## 权威与数据流

### 2026-09-24：基础行为与战术动作拥有关系

- **角色动作方案（ActionSet）只服务基础行为映射**：基础攻击、闪避、技能指令和受击响应等。方案引用某动作不代表角色拥有该战术动作；未引用某动作也不能成为战术卡禁选的依据。不得从默认动作、输入绑定、连招首段或连招后续推导战术动作权限。
- **可以拥有的范围按分类配置**：`Assets/StreamingAssets/MxFramework/CharacterTest/tactical_action_eligibility.json` 为独立权威，每个角色配置 `weaponTypes` 与 `actionTypes`，两维取交集，同一维多个值取并集。`*` 表示该维全部，空数组表示该维不允许任何动作；`unclassified` 表示没有武器标签。动作类型使用 `CharacterActionCategory` 名称（如 `BasicAttack`、`Skill`、`Dodge`）。范围规则不读取角色基础行为方案或当前持有清单。
- **当前拥有是动态数据**：只有 `CharacterTacticalPlayerService`／玩家存档中的集合表示当前拥有。分类允许只产生获取候选，实际获得才加入；移除会解除引用。初始默认清单只初始化新角色／新存档；已有角色重启、修改默认配置或主动清空后都不能重新补发。
- **制作测试与正式使用分开**：AI Lab 可以从全量动作库临时选择符合分类及执行条件的动作，不要求正式持有，也不发放动作。正式绑定、整备确认与新出牌从动态持有集合校验；已确认部署／正在执行／历史冻结继续使用原快照。
- **执行兼容性独立校验**：动作资源、骨架／武器轨迹、有限时长、阶段、命中事件和战术摘要仍检查。不得再以“未装配到角色”“仅基础连招后续”为拒绝战术动作的原因。缺少动作绑定明确报错，不借基础攻击补齐。

当前六个角色的分类范围初值均为两维 `*`，便于后续逐角色收窄；这不授予任何动作。规则修改在重新加载战术服务时进入正式候选范围，已持有存档不因规则变化而自动增删。浏览分类来自独立分类清单，项目生成器同时输出 Editor 目录和 StreamingAssets 运行读取投影。

1. `tactical_content.json`（`Assets/StreamingAssets/MxFramework/CharacterTest/`）声明战术动作的稳定身份和物理动作库引用。行为卡名称、槽声明、费用与版本从现有正式行为卡发布目录投影，不在战术目录复制维护。战术动作不复制动画、Root Motion、碰撞、伤害或测量结果；使用要求继续由真实动作权威判断。
2. `tactical_acquisition.json` 保留临时行为卡获取配置。动作候选由全量动作目录与上述角色分类范围投影；文件中的旧 `actionIds` 只作历史读取，不再决定当前动作获取范围。允许获取不等同于已经拥有。
3. `Authoring/CharacterPackages/<package>/config/character_tactical_defaults.json` 只拥有角色的初始动作、初始行为卡与默认绑定。CharacterStudio 保存，Authoring Compiler 投影至导入包同名配置，Runtime loader 读取。角色包不保存玩家进度。
4. `CharacterTacticalPlayerService` 唯一拥有玩家当前持有集合及绑定。`CharacterTestRuntimeAiPlannerLocalPlayerDeckService` 的 installed-deck 状态只是兼容消费投影，不得继续写另一份战术存档。
5. 玩家侧每个卡牌实例只有“有动作槽 / 无动作槽”两种状态；有槽时保存一个可选动作装配。同一行为卡的两个实例可绑定不同动作。编译器需要的内部定位路径是不可见实现细节，不赋予玩家语义。执行中保持冻结快照。

输入 `LightAttack`、`CharacterActionSlotType` 取消掩码与战术行为卡动作绑定不是同一种数据。旧 `TacticalActionSlot` / resolver 数据保留读取，正式执行必须有明确动作 ID；不会按基础行为映射补齐。旧 `ta.*` 引用与新的 `action:<全局动作ID>` 指向同一物理动作，获得、绑定、移除按此身份兼容，不重复发放同一动作。

## 制作

- CharacterStudio → **默认战术内容**：维护初始战术动作、行为卡和可选动作装配；使用原有保存、撤销和 Unity 导入流程。缺失或不支持的引用显示诊断，不补写默认攻击。
- 行为卡制作：只声明该卡“有动作槽”或“无动作槽”。制作器内部可生成不具业务含义的定位键以连接动作事件，但不得把键名呈现为玩家概念。
- 预览绑定：有动作事件时，从全量目录选择符合角色分类范围及执行条件的动作。选择仅属于制作会话，不写角色默认值或玩家存档。
- 初始化入口：`MxFramework → CharacterTest → Tactical Content → Initialize Missing Character Defaults`。已有明确默认配置继续校验；缺失时生成空的待配置清单及诊断，不再从基础行为方案抽取攻击／闪避作为默认拥有动作。作者需在“默认战术内容”显式配置初始拥有。
- 新正式卡身份须通过现有 Authoring 整数身份目录分配，再运行 `Tools/RuntimeHash/emit_character_ids.py` 生成运行常量，等待 Unity 编译后发布；不在运行时按名称生成整数身份。

## 玩家操作

### 整备中的机制试用卡领取与装配

选中整备中的玩家控制角色，展开顶部工具栏，经「更多 → 领取机制试用卡」领取当前精确发布版本：D417/40定点牵引、41记录回返点、42返回记录点，均为r1。点完成后，点出战卡组旁＋打开当前卡库，再点卡面＋加入出战；三卡均无动作槽，不要求另绑动作。

该入口只写当前进度中选中角色的持有清单，复用 `TryGrantCardForTesting → AddDeckEntry → FlushAsync`；不改默认获取范围、角色初始清单、默认牌组或预设，不自动加入出战。已持有同一精确版本不重复授予；版本未加载时从更多刷新卡库。点击复核角色/entity、弹窗序列与view generation，换角色或旧弹窗回调失效；保存失败保留已授予结果，重试保存不再创建实例。精确r1/hash引用由现行 `CharacterTestFairyGuiTacticalPreparationView.MechanismTrials.cs` 消费正式发布目录。

当前领取→存档重读→卡库装配及过期回调/保存重试原生3项通过，证据归[任务07](../../StorySource/玩法基石/任务/任务07_定点牵引试用切片.md)与[任务08](../../StorySource/玩法基石/任务/任务08_位置回返试用切片.md)；不代表完整自然游玩或新替身/体型机制已实现。

### 整备中的测试获取动作

选中战场角色，将鼠标移到顶部把手展开工具栏，进入「更多 → 测试获取动作」。窗口按动作名称搜索，区分已拥有、可获取与不在获取范围的动作；点击「获取」通过现有持有服务授予当前进度的该角色并保存。动作按物理身份去重，重复点击不重复发放。保存失败可重试。

获取不会修改角色包默认清单、新进度初始授予配置或当前卡牌绑定。完成后关闭窗口，点击卡面中的动作名称即可选择刚获得的动作。未选中角色时入口禁用；切换角色后旧窗口失效，点击时仍重新校验角色范围。此入口是切片测试工具，不代表正式战斗奖励流程。


当前混合切片从首页进入整备，整备卡库只允许使用该进度中当前角色已持有的卡与动作；同一正式定义可装配成多个独立实例。完整操作见[当前 Demo 走查](../Walkthroughs/TACTICAL_CARD_PLAYABLE_DEMO_WALKTHROUGH.md#入口与操作)。既有左右两栏玩家卡组编辑器是另一消费入口，其正式目录浏览范围不能作为切片整备的获取规则。

- 同一行为卡定义可以重复加入；每次加入创建新的单调实例 ID，顺序和动作装配均归该实例所有。
- 有动作槽的卡直接选择并装配一个动作；无动作槽的卡不显示配置入口。
- 既有 CharacterTest 卡组测试入口可浏览全量正式定义并显式“添加测试卡”；这是本机测试清单操作，不回写角色包默认值或 acquisition。当前混合切片整备只消费已持有实例，不借目录浏览、发布或刷新给角色补发全部正式卡；制作测试副本也不等于玩家持有。
- 玩家界面只投影“是否有动作槽”和该实例当前装配的动作，不显示 `slotId`、路径或 resolver。AI Lab 中存在动作槽即表示玩家卡有动作槽；`lightAttackOpener` 是保留读取的历史 resolver 名称，仍需明确绑定战术动作，不能从基础攻击取值，也不得把该槽过滤掉。`stepBack` 仅是内部移动辅助，不投影为玩家动作槽。
- 移除被引用的动作会列出受影响卡牌并确认；确认后一次完成解绑和移除，取消或确认版本过期时不修改任何数据。
- 移除行为卡不删除正式内容。正在执行的卡保持本次快照；新启动重新验证当前持有状态、版本与绑定。
- AI Lab 测试候选继续遵循原有冻结/测试当前修改的会话边界，不把玩家清单修改当成覆写正在运行的制作候选。

角色名单来自已导入角色目录。默认数据不足或资产验证失败的角色显示阻断原因，不生成虚构职业、招式或通用兜底卡组。尚未设计的战斗资源数值只作为显式临时玩法配置，本次不重做三势系统。

## 存档

当前正式切片由 `CharacterTacticalServices.OpenCoreAsync` 打开 SaveGame profile `character-test` 下的 slot `tactical-slice-progress`，序列化入口为 `character-tactical-slice-json-v1`。`CharacterTacticalProgressDto` 的 schema 是 `mx.character-test.tactical-slice-progress.v1`：一个框架 envelope 保存 ActiveProfileId 与多个业务 profile，每份包含玩家清单、整备和已提交结算。通过已有 generation、CAS、恢复机制及候选提交 barrier 原子发布，不再把玩家清单和整备各写一个独立 slot。

首页新建进度保留其他进度；Continue 恢复最近活动进度的战斗外清单和整备。整备的进度选择入口可切换其他已保存 profile，候选验证或保存失败保留原有效服务。此 checkpoint 不保存战斗中的 HP、动作、手牌、冷却或世界权威帧；重新出战从确认部署开始。菜单正式保存入口等待 checkpoint，操作系统强制终止不保证尚未提交的变更。

`tactical_new_game.json` 是当前全新进度的显式初始授予权威；当前配置列出五个角色、各六张卡（共30个授予引用），不是将当前正式目录的23张卡（目录revision37）发给所有角色。既有进度不因新发布、刷新目录或默认配置变化自动补发；缺失或不匹配的正式引用明确阻断。

当前正式打开路径不导入退休的 `tactical-player`、整备旧 slot 或旧 runtime-ai-planner 卡组。玩家 payload 的实例级绑定、单调实例 ID 及已有 v1/v2 反序列化合同仍属该服务的数据层能力，不能据此宣称切片会搜索、迁移那些旧磁盘入口。删除实例不复用其 ID；创建新进度也不等于 tombstone 清除其他 profile。

## 制作测试单卡库

角色测试库和全角色共用测试库位于项目 `Authoring/RuntimeAiLab/TestCards/`，保存基础卡完整配置的独立副本及动作绑定。它们不是玩家当前持有清单，不从基础行为 ActionSet 授权，也不授予动作。基础卡库继续制作／发布；手动测试选卡使用配置后的测试库。仅显式保存更新库版本，本机恢复草稿不影响其他角色。详见[测试卡库说明](../Tasks/CHARACTER_CONFIGURED_TEST_CARD_LIBRARIES.md)。
