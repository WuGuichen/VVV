### 1.1 模块专属检查与单问题节奏

每个实际模块安排专属检查会话，职责登记见[模块检查会话登记表](MODULE_CHECK_SESSION_REGISTRY.md)。范围按当前源码、asmdef 和接口／工具入口划分；同域适配层、Bridge 和测试随模块归属，不把每个目录或程序集都拆成会话。登记表记录职责、排除边界、状态及真实 threadId；未知写“待建立”。既有实现 owner 不自动成为全模块检查 owner，已建的有限联合检查也不代表覆盖了整个框架模块。缺口会话由父按用户确认的清单建立。

不同模块可以并行；**同一检查会话同一时刻只处理一个问题**，包括新问题核实或修复复验。找到首个可靠问题即停止扩查，立即交付触发条件、预期／实际、可观察影响、当前源码位置与 hash／基线、最小证据、与未提交改动的关系、修复方向、难度依据、验证成本及建议机器；不能先攒两三项再报告。证据不足或本轮没有可证问题时明确报告，不以历史日志或缺少测试凑数。

同模块按“发现一个问题→直接提 Issue 并按 §0 指派 xpc／macHermes→用户实施前评审→指定机器修复→独立验收关闭→原检查会话继续下一个问题”循环。检查 owner 在既有授权范围内核实、去重后直接发布与指派，不等待父自动创建本机实现；父接收、协调范围／依赖／验收或明确退回。发现和交办后停止扩查，未验收关闭前不开始同模块下一问题。实现返回时由原检查 owner 按 §5 轻量复核；关闭只结束单个问题，不永久结束模块，也不为每轮另建检查会话。每轮只核实或复验一个问题，不积批次；用户在指定机器自行开启执行，具体任务的明确审批边界仍有效。跨模块根因由父确定一个主责 owner 与协查边界，不重复建 Issue。

检查会话负责问题与修复复验，实现会话负责指定修复，父负责机器／范围指派和必要整合。默认由原模块检查 owner 核对实际 commit／diff、原触发条件、影响边界及实现者自验摘要，父按提交轻量审查；实现者自验不替代独立代码复核。已有自测对应同一修复且通过、独立复核无必修问题时，不强制重跑测试或场景；仅在具体风险或疑点需要时补针对性验证，区分静态、离线、fixture、原生 Runner 和视觉证据。需要 Unity 操作时仍由父安排已有 Editor owner 的窗口，不能因模块并行同时操作同一 Editor。旧待办和正在执行的工作按 §0 核对实际实施状态、候选与交接，不因恢复分发或登记会话而重建 Issue、重复修复或覆盖已在写的工作。

### 1.2 网络模块检查范围与平台停止边界

按用户确认，未来网络模块检查仅限本项目自有代码的功能正确性，例如编解码、队列、连接生命周期、资源释放。自有传输适配只检查本项目代码及其使用的接口合同，不扩查 Unity 引擎或第三方库内部，不连接外部目标，不做攻击模拟、身份冒用或漏洞利用验证。

安全相关疑点只记录源码位置及“待核实”状态；探针未完成或证据不足时不得登记为已证实问题。触发平台限制即停止并报告，不新开替代会话，不改写请求或切换路线绕过限制，也不替受限会话继续执行被拦检查。

### 1.3 性能与代码整理检查

用户新增范围：“现在检查Issue的时候还可以查一查性能优化和代码整理相关的”。后续在既有模块／任务范围内，同时观察功能正确性、性能与维护性；不要求每轮三类各找一项，也不因扩充维度启动全量审计、扩张职责或重查已闭环问题。当前前三批配件／LOD 工作按原授权继续，第四批保持暂停；§1.2 网络范围与原平台／发布限制优先，不通过性能或整理名义恢复受限检查。

- **性能：** 核实真实热点或调用路径，注明入口、触发频率／数据规模及影响。证据可以是当前环境的测量，或明确的静态开销，例如实际路径上的重复分配、重复 I/O、重复计算；说明源码／基线和适用条件。只见循环、文件体积或理论复杂度不是实际性能问题的证明。没有运行测量时标注“静态开销已核实、运行影响待测”，不能写成已测卡顿或已测收益；Issue 指出其与用户目标、预算或合同的关系。
- **代码整理／维护性：** 针对有实际风险或重复维护成本的重复逻辑、职责混杂、废弃路径及依赖耦合，列出当前调用者、具体影响和需同步修改的入口。核对最强反证，例如有意保留的兼容路径、生命周期隔离或合理重复；仅个人命名／格式／拆分偏好不提大改，不把代码行数、缺少可选工具或未采用某模式直接当缺陷。
- **单项提报：** 沿用 §1.1，每模块一次只核实一个问题；首项可靠证据成立即停止扩查，先查当前全部 open／closed Issue 及相关修复，避免换“优化／整理”名称重复提报。正文标注问题类型、精确基线、证据与反证、建议修改边界、难度及依据、建议机器与平台限制、验证成本、原检查 owner 和验收人。
- **实施前评审：** 新 Issue 可在既有发布授权内提报并实际指派，初始执行状态为“待用户实施前评审”；用户评审证据、方案、范围与验收后，记录批准或退回结论，才进入指定机器执行。用户启动会话或明确执行授权须与该评审结论对应，不能仅凭 Issue 已创建、assignee 已设置或检查维度扩充自动开工。已有明确实施授权的任务继续原范围，不重复申请同一授权。
- **收益与回归：** 区分待验证假设、预期收益、静态已确认的开销变化与实测收益。计划用测量验收时，先约定指标／输入规模／环境及可比基线；不能跨平台数字直接推断快慢。整理项先约定行为、API／序列化／生命周期等相关兼容边界及必要回归，不能用“更简洁”代替验收。按 §5 使用最小必要验证，复用对应同一候选的已有证据，不为文档或小型可逆整理默认追加全套测试。

## 2. Gitea 操作优先使用 tea

**Gitea 读写优先使用 tea CLI。** 先以带超时保护的版本／帮助和已有登录配置可用性核验确认当前入口；参数以实际安装版本的帮助为准。只有具体命令不支持，或本次核实 tea 不可用时，才选择其他受支持、已有授权的 API 或浏览器入口。历史超时不代表永久不可用，应按当前操作核实并记录结果。

使用现有正常授权登录能力，不读取或输出凭据，不提取浏览器 cookies，不为此新建 token、改权限、登录新账号或绕过证书警告。登录配置核验只报告必要的仓库／账号匹配和可用性，不披露秘密。缺少认证或支持工具时说明具体障碍；写入须逐项读回，不能由命令已启动推断成功。

用户已授权模块检查会话把既有范围内新发现、经核实且查重的问题直接发布本仓库，并按 §0／§3 实际指派 `xpc` 或 `macHermes`，不逐条再询问。正文保留触发条件、相对路径、精确基线／hash、证据、影响、修复方向、验收、难度及选机理由，当前执行状态写“待用户实施前评审”，通过后写“待指定机器执行”。Issue 发布／指派不等于评审已通过或执行已启动；用户按 §1.3 在对应机器自行开启会话，检查 owner 不自动本机实施。未发布或受限内容仍遵守原停止边界，具体任务的明确审批要求仍有效。

协作评论授权覆盖已指派任务的必要沟通，不扩展为任意公开内部细节、凭据或私有路径的授权。尚未明确允许公开的缺陷内容不得借评论、镜像同步或工具切换绕过原有边界。本文落地不表示任何尚未成功执行的关闭或发布已经完成。

### 2.1 Windows tea 启动超时的已验证处理

本次核验对象是 WinGet 的 Gitea tea `0.16.0` Windows amd64 二进制，文件校验与[安装清单](https://raw.githubusercontent.com/microsoft/winget-pkgs/master/manifests/g/Gitea/tea/0.16.0/Gitea.tea.installer.yaml)一致。原继承环境下的调用曾超时；直接调用真实 exe、仅继承下列环境并在系统临时目录运行后，版本、帮助、已有登录列表、认证读取及授权关闭后的读回均成功。**造成差异的具体环境变量尚未定位**，不能将此写成已彻底查明的原因或全局修复。

先用 `Get-Command tea -All` 核对是否为别名／shim，并解析可执行文件链接。下面路径是本次已验证的 WinGet 位置；其他安装方式应使用其已核实的真实 exe，不据此另行安装或替换版本。

```python
import os
import subprocess
import tempfile
from pathlib import Path

exe = Path(os.environ["LOCALAPPDATA"]) / "Microsoft/WinGet/Packages/Gitea.tea_Microsoft.Winget.Source_8wekyb3d8bbwe/tea.exe"
keys = (
    "SystemRoot", "WINDIR", "ComSpec", "PATH", "PATHEXT", "TEMP", "TMP",
    "USERPROFILE", "LOCALAPPDATA", "APPDATA", "HOMEDRIVE", "HOMEPATH",
    "HOME", "XDG_CONFIG_HOME", "TEA_CONFIG",
)
child_env = {key: os.environ[key] for key in keys if key in os.environ}

def run_tea(*args, timeout=15):
    return subprocess.run(
        [str(exe), *args], cwd=tempfile.gettempdir(), env=child_env,
        capture_output=True, timeout=timeout, check=False,
        creationflags=subprocess.CREATE_NO_WINDOW,
    )

try:
    result = run_tea("--version", timeout=8)
    print("tea version query exit:", result.returncode)
except subprocess.TimeoutExpired:
    print("tea version query timed out; this helper was terminated")
```

该方式只给子进程传递环境，不修改当前会话、用户或系统的全局环境；保留 `HOME`、`XDG_CONFIG_HOME`、`TEA_CONFIG` 供正常已有配置发现，不直接读取或保存凭据文件。

1. 用 8 秒限时核验版本／帮助及 `login list --output json`。列表只提取所需登录名、服务地址和账号匹配，不输出完整配置或含凭据 URL；不反复运行同一已失败探针。
2. 选定已有登录后，以 15 秒限时的 `api --login <登录名> --method GET user` 和 `repos/<owner>/<repo>` 核对服务端身份、精确仓库及所需操作权限。管理员身份不是通用要求；权限不足时如实报告，不提升权限。
3. 写入前冻结编号并复核对象类型／状态；仅执行已授权动作。每项写入后，用同一登录的 GET 读回目标状态，记录退出码及实际结果；超时或读回失败标为未确认，不凭退出码宣称成功。
4. 捕获响应仅用于解析必要摘要，不打印原始认证诊断、账号完整响应或秘密，不启用 debug。记录只含必要身份、仓库、编号、状态和回执，不保存凭据；此启动方法不改变原有内容发布授权。

2026-10-12 已通过本仓库 `repos/vincent/WGameFramework/assignees` 再次读取核实：`xpc`（账号 ID 8）、`macHermes`（账号 ID 2）均可指派。机器不在线不妨碍 Gitea assignee 写入；运行环境与验证能力在执行会话开始时核实，不能由账号可指派推断另一机器已通过测试。

| 执行机器／账号 | 用户描述的渲染能力 | 用户描述的计算能力 | 当前优先任务 |
|---|---|---|---|
| 小主机 `xpc` | 强 | 弱 | 图形、场景、shader、视觉／渲染及确有 Windows 依赖的任务 |

| 本机 `vincent` | 既有描述保留历史 | 既有描述保留历史 | 统筹、只读检查、独立复核；保护已经实际执行中的修复，不默认新增本机实现 |

上述能力是用户描述，未经本项目实测。平台约束先于能力偏好：核对操作系统、Unity／工具版本、原生插件与验证入口；缺少环境如实列实施条件，不猜型号、绝对速度或跨平台通过。只有图形强不代表满足 CPU 重验证需求，只有计算强也不能代替本平台视觉验收。

实际指派写 Issue `assignees` 字段并 GET 读回；正文机器建议不能替代字段。改派时明确原执行状态、交接物、范围和原检查 owner 的独立复审／验收责任；已实际实施者先协调交接，不能由字段变化推断其已停止。用户自行在指派机器开启会话，不要求父连接机器或自动启动。新提报 Issue 的用户实施前评审按 §1.3 执行，具体任务的其它明确审批边界继续有效。

每条任务写简单／中等／困难、依据、验证成本和不确定性。难度供用户选模型，统筹只建议所需能力，不强制具体型号；行数不是风险尺度。

| 难度 | 判断依据与模型能力建议 |
|------|------------------------|
| 简单 | 范围小、约束明确、验证入口稳定；可考虑响应较快的模型。 |
| 中等 | 多个相关文件／模块，需原因定位和回归；建议充分代码推理与验证规划能力。 |
| 困难 | 事务、并发、生命周期、持久化、跨平台或原因未明；建议更强推理与证据核对能力，必要时拆为可验收子任务。 |

验证成本写所需工具、平台、轮次和估计时间，明确哪些是估计。不确定性写尚未复现的现象、缺失环境、待定依赖或未验证风险，不能以难度标签代替说明。

## 4. 指派与本地执行

Issue 正文维护最新目标与验收，至少包含目标、允许范围、禁止触碰文件、Gitea 完整基线 commit、依赖、指派机器及原因、难度及依据、验证成本、不确定性、模块检查 owner／实际 threadId、实现负责人、验收人和验收条件。行为与相关权威说明由同一实现负责人同批维护，见 [QUALITY_GATE §3.1](../QUALITY_GATE.md#31-代码与权威说明同批交付)。

跨机工作保有各机独立本地工作副本，从指明的可获取 Gitea 基线开始。按任务选择独立 clone 或本机 worktree，不让多个会话写同一共享工作目录。**默认同步最新 Gitea `main` 后，只提交本任务改动并正常推送 `main`，不强制任务分支或 PR。** 临时分支仅用于本机隔离或实际交付需要，最终交付默认进入 `main`；仍登记真实基线、候选及工作区状态，不覆盖他人改动。

直接推送前核对任务文件清单、相关权威说明及已有自验摘要，不顺带提交其他任务、个人状态或缓存。先读取／fetch 最新远端 `main`，再快进或普通合并以保留其他机器提交；非快进推送被拒时重新同步后再正常推送。禁止强推，禁止用 `reset`、覆盖 checkout 或清理操作丢弃他人未提交改动。遇同文件冲突先由统筹协调负责人和顺序，不自行选边覆盖。共享工作树或 Editor 正在使用时，在隔离副本完成远端交付，本机同步另行协调。

已有分支候选需要进入 `main` 时，先核对精确修复 commit 与 diff，并确认 `main` 是否已包含该提交或内容一致的修复，避免两机重复合入。父按提交轻量审查；任务明确要求先评审时等待结论，无具体风险或疑点不追加重复测试或场景。推送后读回远端提交号和任务改动，按 §5 核对关闭标准，直接推 `main` 不自动表示已验收。

执行会话开始时：

1. 对新提报 Issue 先核对用户实施前评审结论及实际执行授权，再核对最新正文、评论指派和依赖，与本地基线、远端及工作区状态对应；有差异先说明，不默默换基线。
2. 阅读根及路径上的 `AGENTS.md`，按 [PROJECT_INDEX](../PROJECT_INDEX.md) 进入模块权威，核对已有实现。
3. 在同一 Issue 评论登记开始、机器、会话标签、实际基线及范围；分支按实际填写名称、“不涉及”或“沿用当前分支（实际名称）”。发现已有执行者时由统筹决定继续、拆分或交接。
4. 对已授权范围内的常规实现和可逆修复自主推进；扩大范围、改变依赖、争用共享文件或换负责人，由统筹澄清或重新指派。

依赖写明阻塞关系及交接物，例如已核实提交、文档或回执。依赖未满足时只推进独立部分，不宣称已集成。统筹变更基线、目标、范围或验收时同步更新正文，并评论说明对执行者的影响。

共享文件先明确负责人与修改窗口，避免同时改索引、模块合同、生成器、共享配置或正式资产。交叉任务先拆边界或顺序交接，不通过重复实现解决冲突。重指派在原 Issue 留下暂停点、未提交状态、交接物及新负责人；明确改派前已有 owner 保持负责。

同一机器上同一 Unity 项目只能有一个明确的 Editor 操作负责人。代码会话不能同时刷新、编译、切场景、进入 PlayMode 或写资产。操作前核对用户正在编辑的场景、未保存内容和工具状态；会覆盖／丢弃用户状态的动作先取得具体决定，不能自动保存、重置或恢复成另一份数据。序列化资产写入仍遵循根 `AGENTS.md` 的 Editor／MCP／仓库生成器权威。

## 5. 评论与验收证据

**同一 Issue 是跨机协作记录。** 执行者评论报告开始、阻塞、需要决定、提交及测试证据、交接；统筹评论指派、澄清、评审和确认。正文保存最新目标验收，评论保存过程。其他渠道的关键决定也归入该 Issue，隐藏聊天不能成为唯一记录。已获任务授权的必要评论不逐条重复申请；范围外内容按用户授权处理。

评论记录真实结果与可追溯证据：基线／候选及远端 `main` SHA、修改文件和说明、自验摘要、验证模式、机器／平台、结果及未覆盖范围。按 §4 默认仅提交本任务并直接推 `main`，用户当次限制优先；只有本地修改时写“未提交／未推送”，不能编造交付 commit。日志、完整证据包和额外复跑仅在具体风险或疑点需要时补充。

| 类型 | 能证明的范围 | 不能替代的证据 |
|------|--------------|----------------|
| 离线验证 | 脱离 Unity Editor 的测试、静态检查或独立程序实际结果。 | Unity 编译、Domain Reload、资产导入、原生 Runner 或视觉验收。 |
| 直接 fixture | 直接构造 fixture／调用方法覆盖的逻辑；注明入口与隔离条件。 | 原生 Test Runner 的发现、生命周期、平台和运行结果。 |
| 原生 Runner | Unity Test Runner EditMode／PlayMode 或任务指定运行器；注明模式、候选、环境和结果。 | 未执行的其他平台、Player 构建或视觉交互。 |
| 视觉验收 | 指定候选、场景、运行模式下按步骤观察的画面和交互；附截图／录像与结果。 | 静态图片不能证明交互、持久化或全部行为闭环。 |

静态阅读是定位证据，不是运行通过。普通 Unity C# 默认验证继续按根 `AGENTS.md` 的 refresh／compile、Editor ready 与 Console error 规则；专项测试和视觉验收按任务及适用模块要求执行，不恢复全局 Harness 或额外 `.csproj` 构建要求。

性能项的验收按 Issue 约定报告实际指标、输入／规模、环境及可比基线；静态分析仅证明相应开销路径或操作变化，不证明实测时延、帧率或分配收益。代码整理项复核具体维护风险是否解除和相关行为／兼容边界是否保持；按任务使用已有自验或必要的针对性回归，未执行的验证不写通过。预期收益仍是预期，不能因修复入 main 或 Issue 关闭改写成实测收益。

**默认轻量关闭标准：** 以下三项同时满足即可验收关闭，不强制另跑场景或重复已有测试：

1. 修复已进入 Gitea `main`，已读回精确提交号及任务改动。
2. 实施方自测通过，结果对应主线修复 commit 或内容一致的已验证候选。
3. 原模块检查 owner 独立轻量代码复核无必修问题。

由统筹或其明确指定的原模块检查 owner 核对上述条件并关闭，避免多个会话重复操作。存在具体风险或疑点时，仅补必要的针对性测试，问题解决后再关闭。缺环境、所需测试失败或必修问题未解决时，保留“阻塞／待验收”；未要求的模式列为未覆盖，不自动追加门禁。实现会话不能以自测替代独立复核或自行将未验收任务关闭为完成。

文档和关闭评论须与实际验收结果相符，明确本轮是代码复核、采用已有自测，还是实际重跑了哪项验证；未执行的场景、平台、Player 或测试继续写未执行／未覆盖，不能因关闭 Issue 声称重新跑过或全部通过。

本文不恢复 [ADR-002](../Decisions/ADR-002-Gitea-Agent-Control-Plane.md) 已撤销的全局 Agent Control Plane、强制 PR、Context Pack、固定 Harness 序列或统一提交／合并门禁。需要这些工具时由实际任务明确，日常采用最小必要步骤。

## 6. 本次旧 Issue 清理

用户要求先关闭已有旧 Issue，这是**本次一次性清理动作**。冻结当前未关闭且非 PR 的编号清单，只关闭清单内条目，保留历史，不删除、不触碰 PR、不误关后建条目。逐项写入后读回，记录已关闭、失败和未操作编号；权限或工具不支持时如实报告。

关闭表示旧条目停止跟踪，**不等于问题已修复，也不触发旧任务自动重建**。当前已有工作和待办继续在本机执行，不迁移或重建为新 Issue；后续检查中新发现、经核实的问题才进入新 Issue 指派流程。本规范不声明具体条目已关闭或新 Issue 已发布，也不建立“每次任务都关闭旧 Issue”的永久规则。
