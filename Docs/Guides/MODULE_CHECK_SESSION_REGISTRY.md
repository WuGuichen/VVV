## 6. 登记维护与证据限制

新增会话后父记录准确 threadId、真实标题、最终职责／排除边界及当前状态；没有创建回执或可读会话证据不能填“已建立”。状态区分待建立、核实中、待父接收、待用户实施前评审、已交办待修复、复验中、已验收关闭、下一轮核实中及阻塞；已关闭问题保留 Issue／评论及 main 修复记录，续查记录原 threadId 和新 turn，不把“已建立”或单个问题关闭写成全模块通过验收，也不把“已启动下一轮”写成已有新发现。实现任务 ID 与检查 owner ID 分开维护，Issue 正文登记两者，评论记录单个问题的过程和候选。

职责初稿的结构清点只核对入口，未启动 Unity、未运行模块测试，也未创建会话或 Issue；后续问题发布及实际指派按各 Issue 回执记录，文档提交状态以 Git 历史为准。静态清点发现旧入口需注意：旧 `P/Buffs/` 已移除，Buff v2 在 Gameplay／Combat bridge；`P/Game/`、`P/Preview/` 当前无 C#，不按遗留空目录增加模块；`Logging.md` 仍称无独立 Logging assembly，而当前实有 Logging／Logging.Diagnostics 及 buffer／sink 源码。上述差异仅登记为读图限制，本次不改写其他权威模块合同、不据此自动新建问题。

第三方 FairyGUI、FMOD、MagicaCloth、URP／Transport、Unity MCP／IDE 插件属于依赖或适配边界，挂在对应消费模块或 T12 入口核查，不默认把上游 SDK 全部源码当本项目自主模块。正式资产与 `.meta`、场景、ArtSource／FGUI 源的制作与验证仍按路径规则执行。
