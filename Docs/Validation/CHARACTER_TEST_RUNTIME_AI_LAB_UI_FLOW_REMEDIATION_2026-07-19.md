## 1. 审计目标

从用户点击 Unity Play 开始，按真实操作顺序逐页停留并记录：

1. 当前界面是什么，以及为什么会出现。
2. 用户在该界面应该完成什么任务。
3. 主路径、返回路径和跨页面状态是否明确。
4. 页面是否支持实际操作，而不只是展示调试数据。
5. 信息层级、文字、按钮、留白和反馈是否达到正式编辑器可用标准。
6. 当前表现与目标效果图、Runtime AI Planner 行为卡统一设计之间的差距。

本文件在整个走查期间持续更新。页面未实际打开、未导出 Game 帧缓冲前，不提前判定其验收状态。

## 2. 预期界面流程

```text
Unity Play
→ 玩家行为卡组装配
→ 实验准备 / Setup
→ 行为卡编辑或开始测试
→ 运行中的行为卡时间轴
↔ Facts
↔ Diagnostics · RuntimeFrame
↔ Replay
```

玩家装配层与 Runtime AI Lab 使用同一 Published Behavior Card 和 Installed Deck 语义；Lab 只是在此基础上增加完整 Stage、Detector、Transition、验证、Apply F+1、Replay 和 Publish 能力。

## 4. 页面审计记录

### 01 — Play 默认入口：玩家行为卡组装配

![Play 默认入口的真实 Game 帧](../Images/CharacterTest/runtime-ai-lab-flow-audit-01-play-entry-2026-07-19.png)

预期对照：本页主要对照 [玩家牌库与 Lab 统一工作台](#31-玩家牌库与-runtime-ai-lab-统一工作台) 和 [单点安装、移除与自动组织](#32-单点安装移除与自动组织)。

#### 页面识别

- 当前页面是 `Behavior Deck / 玩家行为卡组装配`，不是 Setup、运行调试页或行为卡逻辑编辑器。
- 当前角色为 `Codex Flow Test (1/1)`。
- 当前卡组为 `3 / 6` 槽、`5 / 10` 费，处于“战前可编辑”状态。
- 左侧是已解锁的行为卡牌库；右侧是当前角色的 Installed Deck。
- 单卡支持安装/移除，并可进入 `Lab 编辑`；页面还提供“应用推荐预设”。

#### 逻辑结论

Play 默认先进入玩家装配层，符合已冻结的 Runtime AI Planner 行为卡玩家玩法与 Runtime AI Lab 统一设计。问题不在于“出现了错误页面”，而在于当前页面没有向第一次进入的用户解释它在完整流程中的位置，也没有给出明确的下一步。

当前最严重的流程问题是：顶部只有“应用推荐预设”和“返回”。从 Play 入口进入时，“返回”并不能表达用户下一步应该去哪里；页面缺少“确认卡组并进入实验设置”或等价主操作。用户无法在数秒内判断：这是启动前的第一步、完整 Lab 首页，还是一个临时弹出的卡组管理页。

#### 问题清单

| 优先级 | 问题 | 影响 |
| --- | --- | --- |
| P0 | 缺少明确的继续主路径；Play 入口却使用“返回” | 用户无法理解如何进入 Setup、编辑或测试 |
| P1 | 页面缺少 `Runtime AI Lab → 玩家装配` 的产品/流程身份 | 容易被误认成孤立卡组页面或完整主界面 |
| P1 | 卡面底部按钮压住用途/风险文字 | 直接破坏阅读与点击判断 |
| P1 | 玩家页面泄漏英文内部风险文本，如 `Base behavior`、`Legacy atomic definition` | 破坏语言一致性，也暴露实现术语 |
| P1 | “安装/移除”和“Lab 编辑”同权并排 | 玩家操作与开发者创作入口层级混乱 |
| P1 | 左侧牌库与右侧已安装卡虽然是同一卡，却没有形成统一卡面语法 | 用户需要重新学习两个区域的阅读方式 |
| P1 | 三个空槽没有槽位编号、费用余量或可安装提示 | 空槽只表现为大块空白，不能引导操作 |
| P1 | 单角色时仍显示左右角色切换按钮和 `1/1` 分页按钮 | 无效控制抢占注意力 |
| P1 | 牌库内容较少时留下大面积无意义空白 | 页面重心上浮，空间利用率差 |
| P2 | “卡组诊断：通过”只在左下角弱提示 | 合法性是关键状态，但缺少与槽位/费用的组合反馈 |
| P2 | 大量装饰性青色/金色按钮边框 | 视觉噪声高于信息层级，和目标图的扁平编辑器风格不一致 |
| P2 | 推荐预设没有说明将安装哪些卡、费用变化及是否覆盖当前选择 | 操作结果不可预判 |

#### 本页整改方案

1. **重建入口语义**
   - 标题改为 `Runtime AI Lab / 玩家行为卡组`，并显示步骤提示 `1. 装配行为卡 → 2. 实验设置 → 3. 测试与调试`。
   - Play 默认入口提供唯一主按钮：`确认卡组并进入实验设置`。
   - `返回`只在确实存在上一级来源页面时显示；作为 Play 根入口时不显示含义不明的返回按钮。
   - “应用推荐预设”降为次要快捷操作，执行前展示将发生的卡组变化。

2. **统一牌库卡与时间轴卡的视觉语法**
   - 牌库卡、已安装卡和行为时间轴卡共用名称、图标、费用、类型色、标签、用途与状态徽标。
   - 牌库卡显示完整摘要；安装区使用同一卡面的紧凑形态，而不是另一套列表条目。
   - `Lab 编辑`改为开发者次级入口或卡面更多菜单，不与玩家的安装/移除主操作争抢层级。

3. **修复卡面排版**
   - 卡面内容按“名称与费用 → 标签 → 用途 → 风险/限制 → 操作”垂直排列，按钮拥有独立操作行。
   - 禁止按钮覆盖正文；正文超长时使用受控行数和详情展开，而不是缩小字号。
   - 所有玩家可见文本使用统一中文显示名；内部 stable ID、Legacy、Base behavior 等实现术语不得泄漏。

4. **重做 Installed Deck 区域**
   - 固定展示 `槽位 1–6`，空槽显示“从左侧选择行为卡安装”。
   - 费用 `5 / 10`、槽位 `3 / 6` 与合法性诊断组合成一个卡组状态区。
   - 安装/移除继续是单点原子操作；自动排列，不要求用户理解物理放置位置。
   - 安装成功、被费用/槽位/重复规则拒绝、卡不可用时，均在操作位置给出即时反馈，同时保留持续卡组诊断。

5. **清理无效控制与留白**
   - 只有一个角色或只有一页牌库时，隐藏而不是禁用左右翻页按钮。
   - 牌库使用可滚动的自适应卡片网格；卡数少时扩大卡面与说明区域，不留下整片空白画布。
   - 普通按钮采用扁平深色样式；青色、金色只用于选中、可安装、警告和主操作状态。

#### 本页验收标准

- 用户首次进入后 3 秒内能回答：“我正在为哪个角色装配卡组，下一步去哪里”。
- 页面存在明确且唯一的“继续到实验设置”主操作。
- 安装、移除、应用推荐预设均能预判结果并获得局部即时反馈。
- 牌库卡、安装卡和后续时间轴卡使用一致的卡面结构。
- 1920×1080 与当前 Game View 窗口下无文字/按钮重叠、裁切和过小字号。
- 玩家可见区域不出现内部 stable ID、Legacy 或英文实现诊断。
- 单角色、单页牌库不显示无效翻页控件。

### 02 — 单点安装“突进连击”后的反馈

![安装行为卡后的真实 Game 帧](../Images/CharacterTest/runtime-ai-lab-flow-audit-02-after-install-2026-07-19.png)

预期对照：本页主要对照 [单点安装、移除与自动组织](#32-单点安装移除与自动组织)。

#### 操作结果

- 单点安装成功，顶部槽位从 `3 / 6` 更新为 `4 / 6`，费用从 `5 / 10` 更新为 `8 / 10`。
- 左侧“突进连击”从“可安装/安装”切换为“已安装/移除”。
- 右侧第四个槽位立即出现“突进连击”，其名称、费用、标签和简介与牌库来源一致。
- “卡组诊断：通过”保持存在，没有被本次操作状态覆盖。
- 页面右下角出现“已安装行为卡”命令反馈。

#### 逻辑结论

Installed Deck 的单点操作、费用/槽位计算、左右投影和持续诊断在本次真实操作中表现正确。行为卡由系统自动进入下一个空槽，用户不需要手工决定物理位置，符合“单点安装、自动组织”的玩家合同。

当前缺口集中在反馈表达，而不是数据正确性。用户点击左侧卡面后，最直接的成功提示出现在屏幕最远的右下角；卡面本身只有静态文案和按钮切换，没有短暂高亮、移动关联或费用变化说明。用户必须同时扫视左卡、右卡、顶部计数和底部状态，才能确认这次操作完整成功。

#### 问题清单

| 优先级 | 问题 | 影响 |
| --- | --- | --- |
| P1 | 成功提示位于远离操作点的右下角 | 用户容易错过，不确定点击是否生效 |
| P1 | 左侧来源卡与右侧目标槽缺少视觉关联 | 无法快速理解卡被安装到了哪里 |
| P1 | 顶部费用从 `5/10` 变为 `8/10`，但没有显示本次 `+3` 与剩余 `2` 费 | 需要用户自行计算，费用约束不直观 |
| P1 | 安装后仍在牌库中完整展示同一卡，并保留同权重“Lab 编辑” | 玩家安装状态与开发者编辑入口继续竞争注意力 |
| P2 | 右侧新卡只是占据下一个条目，没有短暂高亮或插入动画 | 变化在卡组较大时不易发现 |
| P2 | 操作完成后没有推荐下一步 | 用户仍不知道应该继续配卡、进入 Setup 还是开始测试 |

#### 本页整改方案

1. **在操作点闭合反馈**
   - 点击安装后，来源卡立即显示短时成功高亮和 `已安装 · +3费`。
   - 对应 Installed Deck 槽位短时高亮，并可使用轻量连线/移动过渡表达来源与去向。
   - 全局底部状态保留为操作日志，不再承担唯一成功反馈。

2. **把费用变化变成可读状态**
   - 卡组状态区显示 `已用 8 / 10` 与 `剩余 2`。
   - 本次操作短时显示 `费用 +3`；若费用不足，直接在被点击卡面显示所需与缺口。
   - 费用/槽位/重复等拒绝不得只出现在远端诊断区。

3. **保持牌库卡与安装卡一致但不重复噪声**
   - 已安装牌库卡保留用于浏览和移除，但降低操作密度；主状态用明确徽标表达。
   - Installed Deck 卡继续复用相同图标、类型色和标签，采用紧凑形态并显示槽位编号。
   - `Lab 编辑`进入卡面详情或开发者菜单，避免和安装/移除并列为玩家主按钮。

4. **提供流程推进**
   - 合法卡组完成一次操作后，固定主按钮仍为 `确认卡组并进入实验设置`。
   - 不用临时 Toast 替代稳定的流程导航。

#### 本页验收标准

- 点击后不移动视线也能确认安装成功或失败原因。
- 槽位、费用、来源卡状态、目标槽和持续诊断在同一刷新内一致。
- 成功安装明确显示本次费用变化与剩余费用。
- 拒绝操作在被点击卡面局部反馈，且不会覆盖当前卡组诊断。
- 安装卡进入哪个槽位一目了然，同时仍保持自动组织、不要求手工摆放。

### 03 — 应用推荐预设后的反馈

![应用推荐预设后的真实 Game 帧](../Images/CharacterTest/runtime-ai-lab-flow-audit-03-after-recommended-preset-2026-07-19.png)

预期对照：本页主要对照 [单点安装、移除与自动组织](#32-单点安装移除与自动组织)，并要求预设不会绕过玩家构筑的可预判与可撤销原则。

#### 操作结果

- 推荐预设成功替换当前卡组，槽位从 `4 / 6` 回到 `3 / 6`，费用从 `8 / 10` 回到 `5 / 10`。
- 用户刚刚手工安装的“突进连击”被移出当前卡组，左侧恢复为“可安装/安装”，右侧对应槽位恢复为空槽。
- 其他三张推荐卡保持安装状态，卡组诊断继续为“通过”。
- 页面右下角显示“已应用推荐预设”。

#### 逻辑结论

预设应用的数据结果是原子的，左右卡面、槽位、费用和诊断一致，没有出现部分应用状态。但该操作实际是“用推荐清单整体替换当前构筑”，不是无害的推荐提示。当前 UI 在执行前没有告诉用户会移除“突进连击”，也没有列出新增、保留、移除和费用差异；执行后没有一步撤销。一个会覆盖玩家手工选择的操作被表现成普通即时按钮，属于 P0 级交互风险。

#### 问题清单

| 优先级 | 问题 | 影响 |
| --- | --- | --- |
| P0 | 应用前没有展示将移除“突进连击”或整体替换卡组 | 用户构筑在不可预判的情况下被覆盖 |
| P0 | 应用后没有“一步撤销/恢复刚才卡组” | 误触后只能靠手工重建 |
| P1 | 推荐预设没有名称、用途、卡清单、总费用和能力覆盖说明 | 用户无法判断为什么要应用它 |
| P1 | 结果反馈仍只位于远端右下角 | 用户需要自行比较前后页面才能知道发生了什么 |
| P1 | 没有展示差异摘要：新增 0、保留 3、移除 1、费用 -3 | 整体替换行为被隐藏为一句完成提示 |
| P2 | 推荐预设与后续 `Apply F+1` 都使用“应用”动词，但作用域不同 | 容易混淆“改卡组”和“让 Lab 草稿下帧生效” |

#### 本页整改方案

1. **把推荐预设改为有预览的替换操作**
   - 第一次点击打开预设预览，不立即写回卡组。
   - 显示预设名称、用途、完整卡清单、槽位/费用、能力覆盖和合法性结果。
   - 明确列出本次差异：`新增`、`保留`、`移除`、`不可用/不兼容`。

2. **对覆盖用户构筑进行显式确认**
   - 只要会移除或替换当前卡，就必须显示确认按钮 `用此预设替换当前卡组`。
   - 确认区直接列出将被移除的卡，不使用泛化的“部分内容会变化”。
   - 若结果与当前卡组完全相同，按钮显示“当前已是此预设”，不重复写盘。

3. **提供一步撤销**
   - 成功应用后在卡组状态区显示 `已应用：<预设名>` 与 `撤销`。
   - 撤销恢复应用前完整 Installed Deck/hash，并继续通过现有原子持久化边界。
   - 撤销入口至少保留到下一次卡组编辑或离开页面。

4. **区分两种 Apply 语义**
   - 玩家卡组操作使用 `使用推荐卡组` 或 `替换当前卡组`。
   - `Apply F+1`只用于 Lab Draft 向当前 session 候选生效，始终保留其独立名称和说明。
   - Publish 继续是第三个独立门禁，不与上述两种操作复用文案。

#### 本页验收标准

- 应用前能准确看到哪些卡会新增、保留和移除。
- 会移除任何当前卡时必须二次确认，误触一次不会立即覆盖构筑。
- 应用后存在一步撤销，并完整恢复原卡组、费用、槽位和诊断。
- 预设替换、Apply F+1 和 Publish 的名称、作用域和反馈互不混淆。
- 卡组写回仍保持原子性，失败时原 Deck/hash 和持续诊断不变化。

### 04 — 从“突进连击”进入 Lab 编辑

![从玩家牌库进入 Lab 编辑后的真实 Game 帧](../Images/CharacterTest/runtime-ai-lab-flow-audit-04-lab-edit-entry-2026-07-19.png)

预期对照：本页必须同时对照 [行为卡时间轴编辑器](#33-行为卡时间轴编辑器)、[Stage 原地编辑](#34-stage-原地编辑) 和 [运行时读取行为时间轴](#35-运行时读取行为时间轴)。

#### 页面识别

- 用户从玩家牌库的“突进连击”卡点击 `Lab 编辑`进入本页。
- 页面包含行为卡、Facts、RuntimeFrame、Replay 四个工作标签，以及返回、开始测试、撤销、Apply F+1、Publish 等命令。
- 当前时间轴实际包含 `Dash Strike`、`Second Dash`、`Light Attack`、`Light Attack 2` 四个逻辑阶段，符合“突进连击”的内容特征。
- 顶部显示来源 revision 状态，说明页面进入了 Published Card 的 Lab Draft 编辑上下文，而不是直接修改 Published 内容。
- 当前尚未开始测试，预览区与执行摘要处于设计态。

#### 逻辑结论

从玩家卡面进入隔离 COW Draft 的功能链路已经存在，页面也保留了返回、测试、Apply 和 Publish 的必要命令。但用户刚刚点击的是“突进连击”，编辑器主标题却显示“等待/保持”，而时间轴内容又是连续突进与攻击。卡名、Draft 来源和实际逻辑内容没有形成唯一一致的身份表达，属于 P0：用户无法确信正在编辑哪张卡，也无法安全判断 Publish 会更新谁。

即使忽略身份错误，当前编辑器仍是“多轨调试表格”而不是目标中的“大卡片行为时间轴”。四个 Stage 被压缩为细条，执行内容另放在主动作轨，Detector 另放在检测轨，Transition 标签堆叠在底部；用户需要在多个纵向位置拼接同一个 Stage 的语义。右侧固定 Inspector 又占据有效宽度，和“展开时间轴卡片直接编辑”的目标相反。

#### 问题清单

| 优先级 | 问题 | 影响 |
| --- | --- | --- |
| P0 | 从“突进连击”进入，主标题显示“等待/保持” | 编辑与 Publish 对象身份不可信 |
| P0 | 来源 revision、Draft 名称、行为组 Entry 名称和卡内逻辑缺少统一身份栏 | 无法判断当前是 Published、COW Draft 还是 fallback 行为 |
| P1 | 顶部显示 `玩家合法构筑 · 1/6槽 · 3/10费`，与刚才玩家卡组 `3/6、5/10` 不同，却没有说明这是“单卡实验候选” | 用户会误以为实际 Installed Deck 被改变 |
| P1 | Stage、Detector、主动作、Transition 被拆成多条细轨 | 同一 Stage 的完整语义无法一次读完 |
| P1 | 四个 Stage 卡片高度不足，核心信息只能使用很小字体 | 行为卡不是主要阅读和编辑载体 |
| P1 | Transition 标签在底部互相重叠、折行和遮挡 | 分支、失败回退与实际跳转关系不可读 |
| P1 | 固定节点库与 Inspector 同时占用左右空间 | 时间轴有效宽度和卡片尺寸被压缩 |
| P1 | 编辑仍依赖右侧字段和 `±15f` 按钮 | 不符合 Stage 卡内展开、拖动和边缘缩放目标 |
| P1 | 预览相机过远，角色与目标几乎不可辨认 | 无法用预览观察动作效果 |
| P1 | 尚未测试时底部仍显示两条意义不明的蓝白覆盖线 | 误导用户认为存在运行记录或可编辑区段 |
| P2 | `开始测试`、`Apply F+1`、`Publish`缺少作用域说明与状态关系 | 三个生命周期门禁难以区分 |
| P2 | 执行摘要、设计态说明和最近事件占据上半区，但信息稀少 | 大量空间没有服务主要创作任务 |

#### 本页整改方案

1. **先冻结唯一身份栏**
   - 顶部显示 `玩家牌库 > 突进连击 > Lab Draft`。
   - 同一位置展示 Published stable card 的玩家显示名、来源 revision、Draft revision、验证状态和未发布修改状态。
   - 页面标题必须来自当前卡 Draft 的 Published 来源 metadata，不得使用 fallback Action/Entry 显示名覆盖。
   - Publish 对话框再次明确 `突进连击 rN → rN+1`，身份不一致时禁止 Publish。

2. **区分玩家卡组与单卡实验候选**
   - 玩家真实 Installed Deck 状态显示为辅助上下文，例如 `当前玩家卡组：3/6槽 · 5/10费`。
   - 单卡 COW Draft 的合法性改名为 `发布前玩家合法性检查：费用3 · 可安装`，不再显示成另一个 `1/6` 卡组。
   - Lab 越界时显示 `非玩家合法构筑 · Lab 实验`及原因，但不冒充玩家当前卡组已变化。

3. **把 Stage 重建为时间轴上的大卡片**
   - 每个 Stage 卡内直接显示名称、开始/持续时间、DurationMode、执行内容、阶段 Detector、Transition 端口和运行状态。
   - 卡级 Detector 使用时间轴上方独立长卡带；不再用左侧轨道说明文字代替卡片。
   - 主动作是 Stage 内的执行内容，不再复制成另一条主动作轨。
   - Transition 从卡片端口出发，使用带方向曲线连接目标 Stage；前跳、回跳和循环分层布线，禁止标签重叠。

4. **改为卡内原地编辑**
   - 单击 Stage 展开卡片，在卡内编辑开始、持续、目标、结束事件、优先级和高级设置。
   - 拖动卡片修改计划开始时间，拖动右边缘修改计划持续时间。
   - Detector 在所属 Stage 内展开；上下拖动 Detector 修改优先级并提示语义变化。
   - 移除常驻右侧 Inspector；高级少用字段通过卡内二级展开呈现。

5. **回收时间轴有效空间**
   - 节点库改为可收起的添加面板或工具栏菜单，不常驻占用左栏。
   - 下半区除必要的窄工具栏和单行秒/帧标尺外，全部交给可横向、纵向滚动的行为时间轴。
   - 不显示当前无用途的小地图或运行覆盖专轨；运行反馈直接叠加在卡片、Detector 和 Transition 上。
   - 设定可读字号和最小 Stage 卡宽/高；内容多时允许纵向滚动，不通过缩小文字硬塞。

6. **修正上半区观察能力**
   - Preview Camera 自动框选 Agent 与目标，角色高度约占预览区 25%，默认能辨认移动与攻击动作。
   - 未开始测试时展示清晰的设计态预览说明；开始后在卡片时间轴上显示当前 Stage、主动作、Detector 命中和实际路径。
   - 稀疏的执行摘要合并成紧凑状态区，把空间让给场景预览和行为卡牌库。

7. **明确三个生命周期命令**
   - `开始测试`：创建/运行 Lab session，不改变 Published revision。
   - `Apply F+1`：把已验证 Draft 作为当前 session 候选，从下一逻辑帧生效。
   - `Publish`：追加不可变 Published revision，不自动 Apply、不修改当前 evaluator。
   - 三者必须在按钮状态、确认文案和成功反馈中明确区分。

#### 本页验收标准

- 从任何玩家卡进入后，标题、来源 revision、Draft 和时间轴内容始终指向同一卡。
- 用户不查看右侧 Inspector，也能从一个展开 Stage 卡读完并修改其主要语义。
- 1920×1080 下至少四个 Stage 保持可读大卡形态，正文不小于正式编辑器最低字号。
- 所有 Transition 的来源、策略、条件和目标可追踪，无重叠标签。
- 设计态不显示无意义运行覆盖线；运行态反馈直接叠加在 Stage/Detector/Transition 上。
- Preview Camera 中 Agent、目标及动作结果清晰可辨认。
- 玩家 Installed Deck、单卡发布合法性和 Lab 实验越界三种状态不会混淆。

### 05 — 从 Lab 编辑返回玩家牌库

![从 Lab 编辑返回后的真实 Game 帧](../Images/CharacterTest/runtime-ai-lab-flow-audit-05-return-from-lab-edit-2026-07-19.png)

预期对照：本页主要对照 [玩家牌库与 Runtime AI Lab 统一工作台](#31-玩家牌库与-runtime-ai-lab-统一工作台)，验证玩家装配层与 Lab Draft 的双向导航和状态反馈。

#### 操作结果

- 返回后恢复玩家牌库页面，仍为角色 `Codex Flow Test`。
- Installed Deck 保持推荐预设应用后的 `3 / 6` 槽、`5 / 10` 费，没有被隔离 COW Draft 修改。
- “突进连击”仍处于未安装状态，证明进入 Lab 编辑没有隐式安装、Apply 或替换玩家卡组。
- 底部状态显示“已在 Runtime AI Lab 中创建隔离草稿”。
- 顶部右侧返回区域出现 `运行时智能实验室 [F9]` 提示，但与现有返回按钮发生视觉遮挡。

#### 逻辑结论

玩家卡组与 Lab Draft 的数据隔离正确，返回后角色、卡组和推荐预设结果均保持；这符合 COW Draft 不修改 Published、Installed Deck 或当前 session 的合同。

导航和反馈仍不完整。页面仅通过远端底部状态告诉用户已经创建隔离草稿，“突进连击”卡面没有 `已有 Lab Draft`、`未发布修改`或来源 revision 徽标。用户稍后重新进入时无法区分“首次创建”和“继续编辑”。顶部仍使用泛化的“返回”，悬浮提示又覆盖按钮，目的地是 Setup、Runtime AI Lab Shell 还是退出页面并不明确。

#### 问题清单

| 优先级 | 问题 | 影响 |
| --- | --- | --- |
| P1 | 已创建的隔离 Draft 没有回写到对应牌库卡面 | 用户不知道哪张卡存在草稿和未发布修改 |
| P1 | `Lab 编辑`没有根据状态变成“继续编辑” | 首次创建与重开现有 Draft 无法区分 |
| P1 | 返回按钮没有显示目的地 | 用户无法建立页面层级心智模型 |
| P1 | `运行时智能实验室 [F9]`提示层遮挡返回按钮 | 控件文字不可读，快捷键提示制造额外混乱 |
| P2 | “已创建隔离草稿”只显示在右下角状态区 | 与“突进连击”卡面缺少视觉绑定 |
| P2 | 没有显示 Draft 是否已验证、已 Apply、已 Publish | 返回牌库后无法判断后续工作状态 |

#### 本页整改方案

1. **把 Draft 状态绑定回来源卡面**
   - 对应卡显示 `Lab Draft`徽标、Draft revision 和来源 Published revision。
   - 有未发布语义修改时显示 `未发布修改`；仅创建但未修改时显示 `草稿已创建`。
   - `Lab 编辑`根据状态改为 `开始编辑`或`继续编辑`。

2. **明确返回目的地**
   - 从 Lab 编辑返回牌库时，编辑器按钮显示 `返回玩家牌库`。
   - 玩家牌库的上一级按钮显示具体目的地，例如 `进入实验设置`或`返回实验设置`，不继续使用无上下文的“返回”。
   - F9 作为可选快捷键显示在 tooltip 或快捷键帮助中，不覆盖按钮正文。

3. **形成卡面附近的操作闭环**
   - 返回后来源卡短时高亮，并在卡面附近显示“隔离 Draft 已保存”。
   - 底部状态区保留为全局历史，不作为唯一反馈来源。
   - 卡面状态可直接进入继续编辑，也可查看 Draft/Published 差异。

#### 本页验收标准

- 返回后能从卡面直接识别哪张卡存在 Draft、是否有未发布修改。
- 进入 Lab 编辑不会改变 Installed Deck、Published revision 或 session evaluator。
- 每个返回/继续按钮都包含明确目的地，tooltip 不遮挡控件。
- 再次进入同一卡时稳定复用原 Draft，并显示“继续编辑”而不是伪装成首次创建。

### 06 — 从玩家牌库再次“返回”：Runtime AI Lab 被关闭

![关闭 Runtime AI Lab 后的真实 Game 帧](../Images/CharacterTest/runtime-ai-lab-flow-audit-06-lab-closed-2026-07-19.png)

预期对照：本页用于核对文档定义的 `玩家装配 → Setup → 测试`主路径，以及 F9 作为打开/关闭 Runtime AI Lab 的外层命令。

#### 操作结果

- 从玩家牌库再次点击“返回”后，整个 Runtime AI Lab FairyGUI 工作区消失。
- Game View 只剩俯视的 Runtime AI Lab 测试场景和右上角 `运行时智能实验室 [F9]`按钮。
- 没有进入 Setup／实验准备页面，也没有显示角色、行为组、帧上限、出生点或开始实验配置。
- 当前唯一可见操作是使用按钮或 F9 重新打开 Runtime AI Lab。

#### 逻辑结论

当前按钮的真实语义是“关闭 Runtime AI Lab”，不是在 Lab 内返回上一级。该行为本身可以作为外层退出能力保留，但不能继续使用没有目的地的“返回”。更重要的是，权威 UX 设计仍定义 Setup 状态及其角色/行为组、帧上限、出生点与 Start 配置，而当前从 Play 默认玩家装配层出发的正常导航没有暴露 Setup；用户只能关闭 Lab，或从单卡编辑页直接开始测试。

这形成了实际的信息架构冲突：统一玩法文档要求 Lab 默认先显示玩家装配层，UX 文档又要求 Setup 承担实验准备，但实现把“装配层的返回”连接到“关闭 Lab”，没有提供从装配完成继续到实验准备的主路径。

#### 问题清单

| 优先级 | 问题 | 影响 |
| --- | --- | --- |
| P0 | 玩家装配页没有进入 Setup 的主操作，第二次返回直接关闭 Lab | 实验准备页面在正常流程中不可发现或不可达 |
| P0 | “返回”实际执行“关闭 Runtime AI Lab” | 用户无法预判页面会完全消失 |
| P1 | F9 同时像“打开 Lab”按钮和导航 tooltip，但缺少工作区恢复说明 | 用户不知道重开后回到牌库、Setup 还是上次编辑页 |
| P1 | 关闭 Lab 后只剩无说明的俯视测试场景 | 不清楚这是可操作游戏、预览背景还是开发场景 |
| P1 | Setup 与默认玩家装配层的文档关系未在 UI 中实现 | 页面职责无法形成闭环 |
| P2 | 俯视相机过远、角色仅为调试点和文字 | 作为关闭后的宿主画面缺少可读场景状态 |

#### 本页整改方案

1. **冻结外层 Shell 与内层工作区导航**
   - F9 只负责显示/隐藏整个 Runtime AI Lab Shell。
   - Shell 内的玩家装配、Setup、行为卡、Facts、RuntimeFrame 和 Replay 使用独立且可恢复的工作区导航。
   - 关闭 Lab 不等同于任何工作区的“返回”。

2. **闭合玩家装配到 Setup 的主路径**
   - 玩家装配页主按钮固定为 `确认卡组并进入实验设置`。
   - 点击后进入 Setup，并保留当前角色、Installed Deck 和草稿状态。
   - `关闭 Runtime AI Lab`作为次要按钮或 Shell 关闭图标，明确告知会回到测试场景。

3. **明确 Setup 的职责**
   - 只配置本次实验：参与角色/Agent、行为卡组摘要、出生点、帧上限和场景选项。
   - 提供 `返回玩家卡组`与`开始实验`两个明确方向。
   - 不在 Setup 展开卡内 Stage/Detector/Transition；需要编辑时从卡组摘要进入行为卡工作区。

4. **定义 F9 恢复规则**
   - 首次 Play：打开玩家装配层。
   - 主动关闭后再次 F9：恢复关闭前工作区、选中角色、选中卡和滚动位置。
   - 若关闭前处于运行/历史回看，重开后恢复相同 selected/latest frame，不隐式重启 session。

5. **改善关闭后的宿主画面**
   - 若该场景仅为 Runtime AI Lab 宿主，显示简短的 `Runtime AI Lab 已关闭 · F9 重新打开`状态，而不是让用户猜测。
   - 若场景允许直接观察角色，则相机应框选 Agent/目标并保留最小运行 HUD；不能只显示遥远调试点。

#### 本页验收标准

- 玩家装配完成后存在清晰且可达的 Setup 页面。
- “返回玩家卡组”“进入实验设置”“关闭 Runtime AI Lab”是三个不同命令。
- F9 关闭/重开不改变卡组、Draft、session 或历史选择，并恢复关闭前工作区。
- 用户不会因为点击“返回”而意外退出整个 Lab。
- 权威玩法文档、UX Setup 状态表和实际导航图保持一致。

### 07 — F9 重新打开 Runtime AI Lab

![F9 重新打开 Runtime AI Lab 后的真实 Game 帧](../Images/CharacterTest/runtime-ai-lab-flow-audit-07-f9-reopen-2026-07-19.png)

预期对照：本页核对 [玩家牌库与 Runtime AI Lab 统一工作台](#31-玩家牌库与-runtime-ai-lab-统一工作台) 的单一 Shell，以及“关闭/重开恢复关闭瞬间工作区”的导航合同。

#### 操作结果

- 用户关闭 Lab 前最后可见页面是玩家牌库，但 F9 重开后进入了更早的行为卡编辑器。
- 时间轴仍保留四个突进/攻击 Stage 和右侧 `dash`选择，说明部分行为卡编辑上下文仍存在。
- 主标题仍显示“等待/保持”，卡身份错误继续存在。
- Preview Camera 区域变为纯黑，没有恢复关闭前的场景画面。
- 顶部显示“面板已打开”，但没有说明恢复到了哪个工作区或为什么跳过玩家牌库。

#### 逻辑结论

截图能够证明 F9 恢复了错误工作区，并且 Preview Camera 在该路径出现黑帧；它不能单独证明 Player Deck 必然是覆盖层，也不能单独锁定 RenderTexture 生命周期为根因。`ActiveWorkspace`残留、Player Deck 挂载方式、Preview Host 生命周期和 FairyGUI texture 重绑定均属于后续设计切片必须通过源码与运行证据验证的候选假设。

无论最终根因是哪一项，验收合同保持不变：F9 必须恢复关闭瞬间真实可见的正式工作区；如果恢复 Behavior Card，Preview 也必须恢复为可用画面，而不是只恢复文字 ViewModel。

#### 问题清单

| 优先级 | 问题 | 影响 |
| --- | --- | --- |
| P0 | F9 没有恢复关闭瞬间的玩家牌库，而是恢复旧 Behavior Card | 工作区历史与用户可见状态不一致 |
| P2 | Player Deck 可能不是正式互斥工作区，而是独立叠加层（待源码验证） | 若假设成立，导航、返回和状态恢复将难以形成可靠模型 |
| P1 | F9 重开后 Preview Camera 纯黑 | 无法观察场景和角色动作 |
| P1 | “面板已打开”不说明恢复页面、选中卡和 Draft | 反馈对排查上下文没有帮助 |
| P1 | 错误的“等待/保持”标题在重开后继续存在 | 卡身份问题不是瞬时绑定错误，而是稳定投影错误 |
| P2 | 部分选择被恢复、页面却恢复错误 | “状态保存成功”的局部表现反而掩盖导航模型错误 |

#### 本页整改方案

1. **把 Player Deck 纳入正式 ActiveWorkspace**
   - Shell 统一管理 `PlayerDeck`、`Setup`、`BehaviorCard`、`Facts`、`RuntimeFrame`和`Replay`。
   - 一次只能挂载一个正式工作区；Player Deck 不得作为覆盖在 Behavior Card 上的第二棵根 UI。
   - 根 Binder 只负责 Shell、F9 显隐和活动工作区挂载，不使用残留对象显隐模拟页面。

2. **保存用户最后可见状态，而不是底层状态**
   - 关闭 Shell 时记录当前可见 `ActiveWorkspace`、角色、卡、节点选择、滚动位置和 selected frame。
   - F9 重开严格恢复该快照；若快照失效，降级到玩家牌库并给出原因。
   - 从 Player Deck 进入 Behavior Card、从 Behavior Card 返回 Player Deck 都通过显式导航命令更新同一状态机。

3. **修复 Preview Host 生命周期**
   - Behavior Card 挂载时确保 Preview Camera、RenderTexture 和 FairyGUI texture 已创建并绑定。
   - 工作区隐藏时可暂停渲染，但不能留下指向已释放 RenderTexture 的 UI texture。
   - 分辨率变化、F9 隐藏/显示、PlayMode 重载和返回页面均走同一幂等重建路径。
   - 黑帧、缺少 Camera 或 texture 重建失败时显示结构化错误占位，不静默展示纯黑区域。

4. **让重开反馈可验证**
   - 恢复后短时显示 `已恢复：玩家牌库 / Codex Flow Test`或`已恢复：突进连击 Draft`。
   - 不使用没有上下文的“面板已打开”。

#### 本页验收标准

- 在 Player Deck、Setup、Behavior Card、Facts、RuntimeFrame、Replay 任一页面按 F9 关闭并重开，均恢复同一页面和上下文。
- 不存在两个正式工作区同时挂载或通过穿透显隐维持状态。
- Behavior Card 重开后 Preview Camera 第一帧可用，角色/目标构图与关闭前一致。
- 恢复失败时有明确降级页面和结构化原因，不展示黑帧或错误旧页面。

### 10 — 开始测试后的运行中行为卡时间轴

![开始测试后的运行中行为卡真实 Game 帧](../Images/CharacterTest/runtime-ai-lab-flow-audit-08-running-behavior-card-2026-07-19.png)

预期对照：本页核对 [运行时读取行为时间轴](#35-运行时读取行为时间轴) 和“开始测试后留在行为卡工作区”的合同。运行信息应直接覆盖到 Stage 大卡、Detector 和实际 Transition 路径，而不是形成另一套调试轨道。

#### 操作结果

- 点击顶部“开始测试”后仍停留在 Behavior Card 工作区，没有强制跳转到 Facts 或独立 Live 页面；这一条导航合同通过。
- 顶部状态显示 `测试已开`，RuntimeFrame 控制显示选中帧与最新帧均为 `3`，同时全局状态为“已暂停”。
- F9 重开时的黑色 Preview Camera 在会话启动后恢复，能够看到 Agent、目标、目标连线和范围圆。
- 页面主标题与预览标题仍为“等待/保持”，运行状态显示主动作 `Wait or hold`；但时间轴内容仍是 `Dash Strike`、`Second Dash`、`Light Attack`、`Light Attack 2`，右侧选择仍为 `dash`。
- 时间轴增加了青色运行线和底部实际状态文字，但没有把“当前 Stage、已执行比例、活跃 Detector、命中事件、实际跳转”明确覆盖到对应的大卡和连线上。
- Transition 标签在多个水平箭头上密集堆叠、折行并互相遮挡，运行后比静态状态更难辨认实际采用了哪条路径。

#### 逻辑结论

“开始测试不离开编辑器”的主链路已经存在，紧凑 RuntimeFrame 控制条和嵌入式预览也已接通，说明运行数据并非完全缺失。但当前页面无法回答最核心的三个问题：**正在测试哪张行为卡、当前执行到哪张 Stage 卡、为什么跳到下一张卡**。

最严重的是运行身份矛盾。用户从“突进连击”进入 Lab，时间轴也是突进/攻击序列；开始测试后，页面和 runtime 却稳定显示“等待/保持 / Wait or hold”。UI 没有说明当前运行的是 Published baseline、未 Apply 的旧候选、免费 fallback，还是选中的 COW Draft。只显示 `测试已开` 会让用户误以为正在验证所见时间轴，实际运行对象却可能不同。这是发布与调试安全边界上的 P0 问题，不只是标题文案错误。

其次，运行态仍使用“额外轨道”表达：底部青色/白色水平线和一句 `实际：...` 与 Stage 卡分离，Detector 与 Transition 也没有清晰的 Armed、Active、Hit、Pending、Committed 状态。用户必须在预览、中央文字状态、右侧摘要、Stage 轨、主动作轨和底部覆盖线之间拼接同一帧语义，违背“行为卡本身是主要阅读与编辑载体”的已定方向。

#### 问题清单

| 优先级 | 问题 | 影响 |
| --- | --- | --- |
| P0 | 所见时间轴是“突进连击”，运行标题与主动作却是“等待/保持 / Wait or hold” | 无法证明正在测试所编辑 Draft，测试结果不可作为 Apply/Publish 依据 |
| P0 | 未显示运行对象身份：Published revision、Draft hash、session candidate 与 Apply F+1 状态 | 无法区分基线运行、Draft 候选、Installed Deck 仲裁或 fallback |
| P1 | 当前 Stage 和主动作没有在对应 Stage 大卡上形成唯一强高亮 | 用户无法一眼定位当前逻辑位置 |
| P1 | Detector 没有在卡上显示 Armed、Active、Hit、Rearmed 状态 | 无法理解为何尚未跳转或哪个事件胜出 |
| P1 | 实际 Transition 路径仍是多条重叠细线和标签 | 前跳、失败、完成和回退路径不可追踪 |
| P1 | 运行覆盖层仍是底部意义不明的青/白水平线 | 占用编辑高度，却不能映射到具体卡片或事件 |
| P1 | Preview 中角色过小、均为白色轮廓，动作姿态难辨 | 即使相机恢复，也无法观察突进、攻击与中断表现 |
| P1 | 点击“开始测试”后直接处于暂停帧 3，但缺少“会话已创建、等待播放”的强提示 | 用户可能误以为测试正在运行，实际帧不再推进 |
| P2 | 上方中央状态与右侧摘要信息稀疏，仍保留大量空白 | 预览和时间轴可用空间被低价值容器占据 |
| P2 | 帧控制按钮装饰描边密集、标签较小 | 高频播放/步进操作难以快速扫读 |

#### 本页整改方案

1. **冻结“编辑对象”和“运行对象”双身份条**
   - 页面标题始终来自当前行为卡 Draft，例如 `突进连击 · Lab Draft`，不得由当前 runtime action 或 fallback 名称覆盖。
   - 运行区固定显示 `正在运行：<stable card> · Published rN / Draft candidate <hash>`，并显示 `已应用 F+1`、`尚未应用`或`运行基线`。
   - 若运行对象与编辑对象不一致，用明显但不遮挡的状态条说明原因，并提供 `测试当前 Draft`或`Apply F+1 后继续`；不得静默显示“测试已开”。
   - 身份链不一致、candidate hash 不可解析或运行对象不可证明时禁止把测试标记为可发布验证。

2. **把运行态直接投影到 Stage 大卡**
   - 当前 Stage 卡使用唯一高亮外框、执行图标和卡内进度填充；右上角显示 `当前 · Frame N`。
   - 卡内主动作显示 `Pending / Starting / Running / Canceling / Completed / Failed`，以及计划时长与本次实际耗时。
   - Stage 切换时逻辑游标跳到目标卡，不沿秒尺匀速播放；秒/帧标尺只表达计划窗口和实际耗时参考。
   - 历史帧回看时同一套卡面恢复当时状态，不另建历史专用布局。

3. **把 Detector 和 Transition 状态绑定回卡片**
   - 卡级 Detector 使用可纵向滚动的长卡带；阶段级 Detector 收进所属 Stage 卡的展开区。
   - `Armed`使用稳定弱高亮，`Active`使用持续点亮，`Hit`短时闪烁，`Rearmed`显示重新武装标记。
   - Transition 从 Stage 卡端口以分层方向曲线连到目标卡；本帧获胜路径加粗并显示事件、优先级和策略，未胜出的同帧事件降级显示。
   - `Pending / Transitioning / Committed`必须是单一路径状态，不用两个主动作卡同时高亮伪装过渡。

4. **删除独立且不可解释的运行覆盖轨**
   - 移除底部青色/白色长条及孤立的 `实际：...`文本。
   - 计划时间保留在 Stage 卡宽度和单行秒/帧标尺中；最近实际耗时以卡内细覆盖条表达。
   - 回收的高度全部交给 Stage 卡、Detector 卡和纵向滚动，不恢复当前缩略图或小地图。

5. **让 Preview 真正支持动作观察**
   - 自动框选 Agent 与当前目标，同时保证 Agent 高度约占预览区 25%；二者距离过大时优先保持动作角色可辨并用边缘目标指示器补足目标方向。
   - 使用阵营色、选中轮廓和动作状态标记区分 Agent 与目标，保留目标线、移动方向、攻击范围和危险提示。
   - 播放时连续展示动作，单帧回看时恢复离散姿态；Preview、Stage 卡高亮和 selected RuntimeFrame 必须使用同一恢复结果。

6. **明确会话启动与播放是两个状态**
   - “开始测试”完成后显示 `会话已创建 · 当前暂停在 Frame 3`，主操作变为清晰的播放按钮。
   - 若产品决定开始测试自动播放，则按钮必须真正推进帧；若保留暂停启动，则在点击前后都说明该规则。
   - 帧控制保持两行：第一行播放、步进、帧输入与跳转；第二行拖拽轨道、selected/latest/limit、Warm Replay 和分支提示。

7. **压缩上半区低价值容器**
   - 预览占主要宽度；运行身份、当前 Stage/动作、目标和最近事件合并为一个紧凑摘要区。
   - 没有事件时不保留大面积空框，以最小空状态呈现；新增空间优先给 Preview 和下方时间轴。

#### 本页验收标准

- 从任一行为卡开始测试后，页面标题、Draft、candidate、runtime card 和 hash 能形成可核对的完整身份链。
- 若运行的是 Published baseline 或 fallback，而不是当前 Draft，页面必须明确显示差异，不能伪装成正在测试所见时间轴。
- 当前 Stage、主动作状态、活跃/命中 Detector 和实际 Transition 路径无需查看独立摘要即可直接从卡片读出。
- 运行态不新增底部专用覆盖轨；纵向空间用于可滚动的大 Stage/Detector 卡。
- Preview 中动作角色清晰可辨，播放、暂停、步进和历史回看均与时间轴卡面同步。
- 开始测试后的暂停/播放状态与帧是否推进完全一致，并有明确反馈。
- 1920×1080 下 Transition 标签无重叠、折行遮挡或路径歧义。

### 11 — Facts 运行事实诊断

![Facts 页真实 Game 帧](../Images/CharacterTest/runtime-ai-lab-flow-audit-09-facts-2026-07-19.png)

预期对照：Facts 是独立、只读的当前帧事实与决策因果诊断页。它不显示行为卡编辑控件，也不代替 RuntimeFrame 的五轨历史；其核心任务是回答“当前有哪些权威事实、它们从哪里来、哪些事实令哪个候选胜出”。

#### 操作结果

- 从运行中的 Behavior Card 点击 `Facts` 后成功切换到独立页面，行为卡时间轴、节点库和 Inspector 没有继续穿透显示。
- 顶部仍显示暂停状态、选中帧 `3`和四个工作标签；页面右侧“实时监视”也标记为 `RuntimeFrame 3`。
- 左侧 Agent 区列出两个 Agent 和原始路径；右侧显示执行摘要、因果路径、事实、检测器、候选决策和最近事件，并提供“定位行为节点”“定位 RuntimeFrame”。
- 页面中心大面积直接显示主游戏场景，Facts 内容仅占左侧窄栏、右侧面板和底部事件历史；底部历史当前只有一行。
- 同一帧同时显示 `Dash Strike · Running`、右上“等待”、候选决策 `Wait or hold 300`、运行命令 `none`，但没有标明它们分别是当前 Stage、当前主动作、下一帧候选还是 fallback。

#### 逻辑结论

Facts 的页面边界和跨页定位入口已经有雏形，但信息架构仍以“散落的调试文字”而非“事实工作台”组织。当前最显眼的区域是没有交互价值的主场景穿透，真正需要对照的事实值、来源、更新时间、检测状态和候选裁决却采用小字号段落挤在右侧。用户无法横向比较事实，也无法从候选决策反查是哪条事实改变了结果。

`Dash Strike Running`与`Wait or hold`不一定在运行语义上必然冲突——它们可能分别表示当前阶段和下一次候选——但 UI 没有给出时间与职责标签，因此表现为互相矛盾。Facts 页必须明确区分“当前已提交状态”“本帧观察事实”“本帧候选裁决”“下一帧待提交结果”，不能要求用户根据内部字段猜测。

#### 问题清单

| 优先级 | 问题 | 影响 |
| --- | --- | --- |
| P0 | `Dash Strike Running`、`Wait or hold`、`等待`与`运行命令 none`缺少时序和职责标签 | 无法判断当前真正执行的行为及下一步裁决 |
| P1 | Facts 工作区没有全尺寸不透明底板，主场景大面积穿透 | 诊断信息被背景干扰，页面不像独立工作区 |
| P1 | 缺少结构化事实表：名称、值、来源、更新时间、权威性和变化状态 | 无法比较、筛选或追踪事实来源 |
| P1 | 因果路径、事实、检测器和候选决策挤在同一小面板 | 决策链阅读顺序不清，文字过小 |
| P1 | Agent 列表显示 `root/fallback`等内部路径且没有明确选中态 | 多 Agent 上下文难以确认，开发标识噪声过高 |
| P1 | 底部事件历史占据整行高度却只有散文式单行文本 | 空间利用率低，事实变化不可逐项扫描 |
| P1 | 当前选中帧、最新帧、Live/History 状态只散落在顶栏文字中 | 容易把历史事实误认成实时状态 |
| P2 | 顶部出现多组描边按钮，部分命令与 Facts 阅读任务关系不明 | 工作区主次不清，增加视觉噪声 |
| P2 | “定位行为节点”“定位 RuntimeFrame”只作为右下普通按钮出现 | 很好的联动能力不够贴近具体事实或因果节点 |

#### 本页整改方案

1. **把 Facts 重建为全尺寸不透明诊断工作区**
   - Shell 标签栏以下使用统一深色不透明底板，不显示主场景；场景观察只留在 Behavior Card 的 Preview Camera。
   - 顶部上下文条固定显示 `Agent`、`Selected Frame / Latest Frame`、`Live / History`、authority hash 和当前 session candidate。
   - Facts 页面不挂载 Behavior Card 编辑控件，也不复制完整 RuntimeFrame 时间轴。

2. **以结构化事实表作为页面主体**
   - 按 `感知`、`目标`、`自身状态`、`动作可用性`、`冷却/资源`、`Planner`分组。
   - 每行显示事实名称、当前值、来源系统、最后更新帧、有效期/新鲜度、authority/predicted 属性和相较上一帧的变化。
   - 支持搜索、仅看变化、仅看参与本帧裁决、固定关注项和复制原始稳定 ID。
   - 面向用户的中文名称作为主标签，原始 fact/path ID 放在次级文本或 tooltip，不直接抢占主阅读层。

3. **把决策因果链变成明确的四段投影**
   - `上一帧已提交状态`：当前行为卡、Stage、主动作和 Pending Transition。
   - `本帧观察事实`：实际进入 evaluator 且影响结果的事实快照。
   - `本帧裁决`：候选、分数/优先级、被淘汰原因和胜出项。
   - `提交结果`：本帧是否提交跳转、下一帧将采用的行为/Stage，以及为何保持当前状态。
   - 若 `Dash Strike`是当前执行、`Wait or hold`是下一候选，必须在这四段中分别归位；若身份链真的冲突，则显示诊断错误。

4. **让 Agent 选择和帧上下文可验证**
   - Agent 列表使用角色名、稳定 ID、当前行为图标和状态，明确高亮当前选择。
   - 切换 Agent 后事实表、因果链和事件历史在同一刷新内同步，不保留上一 Agent 的残留字段。
   - 历史帧使用醒目的 `历史回看 · Frame N`状态；返回最新帧恢复 `Live`，不依赖顶栏散文提示。

5. **把事件历史改为紧凑的 typed fact delta 列表**
   - 每行显示帧号、Fact、旧值→新值、来源和关联裁决；支持点击定位对应事实行。
   - 点击“定位 RuntimeFrame”进入五轨历史并选中对应 typed marker；返回后恢复 Agent、事实筛选和滚动位置。
   - 点击因果节点或候选可“定位行为节点”，回到 Behavior Card 并高亮相应 Stage/Detector/Transition，而不是只提供全局按钮。

6. **压缩全局命令并提高可读性**
   - Facts 页保留必要的播放/暂停、单帧步进和工作区切换；编辑、Publish 等行为卡命令不进入 Facts 主工具栏。
   - 统一标题、表头、正文和辅助 ID 字号；1920×1080 下事实值与淘汰原因无需放大即可阅读。

#### 本页验收标准

- Facts 页完全不透明且没有行为卡编辑器或主场景穿透。
- 任一帧都能明确区分当前已提交行为、本帧事实、本帧候选和下一帧提交结果。
- 所有参与裁决的事实均能查看值、来源、最后更新帧和权威属性，并可从候选反向定位。
- 多 Agent 切换不会混合数据，当前 Agent 和 Selected/Latest Frame 始终醒目可见。
- Facts 的事件历史只展示 typed fact delta；完整五轨分析仍由 RuntimeFrame 页面负责。
- 从事实或因果节点跳转 Behavior Card/RuntimeFrame 后可返回并恢复筛选、选择与滚动上下文。
- 1920×1080 下无需依赖小字号散文段落即可读懂一次完整决策。

### 12 — RuntimeFrame 五轨历史

![RuntimeFrame 页真实 Game 帧](../Images/CharacterTest/runtime-ai-lab-flow-audit-10-runtime-frame-2026-07-19.png)

预期对照：RuntimeFrame 是真实运行帧的完整历史分析页，负责 Revision、Decision、Action、Hit/Damage、Warning 五类 typed marker、历史定位、A/B 区间和显式分支重算；它不编辑行为卡计划时间。

#### 操作结果

- 从 Facts 点击 `RuntimeFrame` 后成功切换到独立五轨页面，顶部提示“已打开 RuntimeFrame 调试页”。
- 当前会话顶栏仍显示已暂停、选中帧 `3`且为最新帧；底部中央也只显示一个孤立的 `3`。
- 时间标尺从当前帧附近一直展开到约 `900`，大多数轨道区域为空。
- Revision、Decision、Action、Hit/Damage、Warning 五种颜色和英文图例集中挤在最上方窄区；左侧又有“版本、决策、动作、命中/伤害、警告”五个大分区。
- 在标尺约 250、380、550 的位置可见三个菱形标记，但页面没有显示其类型、帧号、来源或详情；它们与“最新帧 3”的关系无法解释。
- 底部存在首帧/前后步进、播放、最新帧、推进、跳转、A/B、循环和“从此重算”等能力雏形，但字号、图标和当前状态非常小，未形成清晰操作顺序。

#### 逻辑结论

五轨历史和分支控制的功能入口已被放进独立页面，页面职责方向正确；但当前投影没有建立“数据有效范围”。在最新帧仅为 3 的情况下，视口仍铺满到 900，并在未来区出现无来源菱形标记。它们可能是静态装饰、对象池残留、错误缩放或真实 marker 被错误映射；无论原因是哪一种，用户都会把它们理解为已经发生的历史事件。这属于 P0 级权威诊断风险。

当前页面还把五种细图例线和五个大轨道分区重复表达。真正发生的少量帧被压缩在最左侧，而未模拟未来占据绝大多数屏幕；没有醒目的 selected-frame 游标、captured/unsimulated/evicted 区域，也没有 marker 详情。因而页面虽然“像时间轴”，却还不能支持定位一次行为跳转、命中或警告。

#### 问题清单

| 优先级 | 问题 | 影响 |
| --- | --- | --- |
| P0 | 最新帧为 3，却在约 250/380/550 帧位置显示无来源菱形标记 | 未来未模拟数据可能被误认成真实 typed event |
| P0 | 未区分已捕获、尚未模拟和已淘汰区间 | 用户无法判断哪些帧可恢复、哪些帧尚不存在 |
| P1 | 默认视口直接铺到帧上限约 900，而当前只有极少历史 | 真实事件被挤压，绝大多数编辑面积无效 |
| P1 | 五种图例细线与五个大轨道分区重复且对应关系不清 | 轨道层级和 marker 类型难以建立映射 |
| P1 | 缺少明确的 selected-frame 垂直游标和最新帧边界 | 无法确认当前预览/事实恢复到哪个时间位置 |
| P1 | 菱形 marker 没有标签、帧号、类型、Agent 或详情投影 | 无法用于诊断和跨页定位 |
| P1 | 底部控制过小，播放、步进、跳转、A/B、循环、推进与重算没有分组 | 高频操作容易误触，分支操作风险不可见 |
| P1 | “从此重算”与普通播放控制同级，没有影响范围和确认状态 | 可能误把只读回看变成破坏未来的分支操作 |
| P2 | 页面四周仍可看到宿主场景色块 | 正式诊断工作区的背景层不完整 |
| P2 | 空轨道没有说明“当前尚无此类事件” | 用户难以区分无事件、加载失败和投影失败 |

#### 本页整改方案

1. **先建立权威帧区间投影**
   - ViewModel 明确提供 `oldestRetained`、`selected`、`latest`、`frameLimit`和 seek/branch 状态。
   - 已捕获区使用正常轨道背景；尚未模拟区使用明显弱化背景；已淘汰区使用不可恢复斜纹并显示最老保留帧。
   - marker 只能来自 typed TimelineRecord，且帧号必须落在可解释区间；对象池复用时必须清除旧 marker、标签和选中状态。
   - 若发现 marker 超出 latest 或类型无法解析，显示结构化投影错误并停止把该 marker 画成真实历史。

2. **使用适合当前数据量的默认视口**
   - 初次进入自动框选 retained range，并保留最小可读窗口，例如 60 帧；只有用户选择“查看帧上限”时才铺到完整 900。
   - 提供缩放、横向滚动、适配已捕获范围和回到 selected frame；缩放不改变 selected/latest。
   - 帧数很少时将 marker 保持可点击尺寸，不把前三帧压成左侧一条线。

3. **把五轨变成唯一、不重复的 typed lanes**
   - 固定五轨：Revision、Decision、Action、Hit/Damage、Warning；左侧使用中文主名和颜色图例，不在顶部再复制一套细轨。
   - marker 显示紧凑图标和短标签；同帧多事件聚合为带数量的 stack，展开后按稳定顺序显示。
   - 空轨道显示轻量的“当前区间无事件”，不保留无法解释的大面积空框。

4. **增加 marker 详情与跨页联动**
   - 点击 marker 打开就近详情卡：帧号、Agent、typed event、来源、authority hash 和相关 stable ID。
   - Decision/Action marker 可定位 Behavior Card 的 Stage/Detector/Transition；Hit/Warning 可定位场景实体或 Facts；所有跳转返回后恢复本页视口和 marker 选择。
   - 从 Behavior Card 点击实际 Transition 进入本页时，直接选中对应 `TransitionCommitted` marker，而不是只打开标签页。

5. **把 selected-frame 控制重组为两层**
   - 时间轴内使用醒目的垂直游标和帧号气泡；右侧固定显示 `选中 N / 最新 M / 上限 L`。
   - 第一组为首帧、-10、-1、播放/暂停、+1、+10、最新和帧输入跳转。
   - 第二组为 A/B、循环、推进未来和 Warm Replay 状态；只读回看与生成未来使用不同视觉分组。
   - 拖动开始自动暂停；历史回放到 latest 后才恢复实时推进。

6. **隔离破坏性分支重算**
   - 历史帧默认只读，不截断已有未来。
   - 只有 selected < latest 时才显示 `从 Frame N 建立新分支`，同时展示将失效的 `N+1…latest`范围和确认步骤。
   - 重算中禁用重复操作，失败恢复原分支和操作前 selected frame；不得与普通播放按钮同级无提示执行。

7. **完成工作区视觉底板和错误状态**
   - RuntimeFrame 页面使用全尺寸不透明底板，不显示宿主场景。
   - 数据尚未捕获、记录加载失败、marker 投影失败分别显示不同空/错状态，不以空白轨道代替诊断。

#### 本页验收标准

- latest 为 3 时不会在 3 之后显示任何伪历史 marker；尚未模拟区与真实捕获区一眼可分。
- 五轨中的每个可见 marker 都能追溯到 typed TimelineRecord，并显示准确帧号、类型和 Agent。
- selected 游标、Preview/Facts/Behavior Card 历史状态始终指向同一 RuntimeFrame。
- 默认视口自动适配 retained history，少量帧不会被 900 帧上限压缩到不可用。
- A/B 与循环只读回放不会修改历史；“从此重算”必须显示影响范围并显式确认。
- 从行为卡跳转可定位到准确 marker，返回后恢复原行为卡视口；反向联动同样成立。
- 1920×1080 下轨道、marker、控制和详情可读，无宿主场景穿透。

### 13 — Replay 回放与确定性验证

![Replay 页真实 Game 帧](../Images/CharacterTest/runtime-ai-lab-flow-audit-11-replay-2026-07-19.png)

预期对照：Replay 负责选择或承接一段权威记录、恢复 bootstrap、逐帧回放并验证确定性。它可以复用 RuntimeFrame 的五轨可视组件，但必须额外回答“回放什么、以什么初始权威状态恢复、验证是否通过、若失败首先在哪里分歧”。

#### 操作结果

- 点击 `Replay` 后成功切换到标为“Replay 回放验证”的独立页面。
- 页面主体、0～900 标尺、五轨、三个菱形标记和底部控制与 RuntimeFrame 页几乎完全相同，仅背景更深、左上标题不同。
- 当前仍显示选中/最新帧 `3`，但约 250、380、550 位置的无来源 marker 继续存在。
- 页面没有显示 replay 记录来源、记录 ID、录制范围、bootstrap snapshot、catalog hash、session authority hash 或当前验证模式。
- 页面没有“开始验证/停止验证”、恢复进度、逐帧 hash 结果、通过/失败结论、首个分歧帧或预期/实际值。
- 也没有说明当前是在浏览 live session 历史、Warm Replay 恢复结果，还是独立 replay playback。

#### 逻辑结论

当前 Replay 只是 RuntimeFrame 五轨的另一个外观入口，不是可验收的回放验证工作区。用户看不到任何 replay-specific 输入、状态或结果，无法证明 bootstrap 被实际恢复、Published catalog 与固定 revision 被校验，也无法证明每帧 authority hash 与录制值一致。标题中的“回放验证”因而是未经 UI 证据支撑的能力声明，属于 P0。

复用五轨本身是正确的维护方向，不应为了 Replay 再实现一套时间轴；问题在于复用后缺少 Replay 壳层和验证投影。Replay 应在五轨上方/侧边提供记录来源与验证摘要，并在发现分歧时把五轨定位到首个错误 marker。它还必须和 live RuntimeFrame 区分，防止用户把当前 session 的浏览误认成已经完成确定性回放。

#### 问题清单

| 优先级 | 问题 | 影响 |
| --- | --- | --- |
| P0 | 页面没有 replay 来源、bootstrap 恢复状态或确定性验证结果 | 无法证明真正执行了回放与权威校验 |
| P0 | Live history、Warm Replay 和独立 Replay playback 没有模式区分 | 用户可能把普通历史浏览误认成验证通过 |
| P0 | 与 RuntimeFrame 相同的未来无来源 marker 继续出现 | 回放证据包含无法解释的数据，验证结论不可信 |
| P1 | 缺少 catalog/session authority/replay hash 身份链 | 无法判断回放使用了哪个 Published revision 与会话 roster |
| P1 | 缺少逐帧 expected/actual hash 和首个 divergence 定位 | 验证失败时无法诊断参与者或字段 |
| P1 | 没有开始、取消、重试、进度和完成状态 | 不知道验证是否尚未运行、正在运行还是已经完成 |
| P1 | Replay 直接复制五轨页面而没有独立信息架构 | 页面职责不可辨，维护上也容易出现两套状态分支 |
| P1 | 记录为空或只有三帧时没有可理解的空/短记录状态 | 大面积空白和未来标尺掩盖实际记录范围 |
| P2 | 控制条仍使用 RuntimeFrame 的“推进+1、从此重算”等 live 命令 | 回放验证与生成新未来的权限边界混淆 |

#### 本页整改方案

1. **复用一个 RuntimeFrameTimeline Composite，而不是复制页面**
   - RuntimeFrame 与 Replay 共用经修正的五轨、marker、游标、缩放和详情组件。
   - RuntimeFrame 壳层负责 live 历史、seek 和显式分支重算；Replay 壳层负责记录选择、bootstrap 恢复和确定性验证。
   - Replay 模式不显示会修改 live future 的“推进+1”“从此重算”；需要派生实验时使用单独的“从回放帧创建 Lab 分支”流程。

2. **建立可核对的 Replay 身份摘要**
   - 显示 replay ID/文件或内存记录来源、录制时间、frame range、agent count、schema/version 和记录完整性。
   - 显示 Published catalog hash、session authority bootstrap hash、固定 card revision/deck hash 和 gameplay bootstrap hash。
   - bootstrap 恢复后从实际恢复状态重新推导 authority hash；不得只信任 replay envelope 中的旁路字符串。

3. **把验证过程表达成明确状态机**
   - `未验证 → 校验记录 → 恢复 Bootstrap → 逐帧回放 → 完成/分歧/失败`。
   - 每一步显示进度、耗时和结构化错误；运行中允许安全取消，取消不污染 live session。
   - 只有完成所有帧并验证 bootstrap/catalog/participant hash 后才显示 `Deterministic · Passed`。

4. **提供首个分歧诊断**
   - 失败摘要显示 first divergent frame、participant/module、expected hash、actual hash 和最近 typed events。
   - 五轨自动定位该帧并高亮 Warning marker；详情可展开各 participant hash，但不使用大段不可扫描日志。
   - 支持从分歧帧定位 Facts、Behavior Card Stage/Transition 和相关场景实体；返回后保持失败上下文。

5. **区分三种时间状态**
   - `Live History`：当前 session 的已捕获记录，只读浏览或显式分支。
   - `Warm Replay`：为历史 seek 恢复权威状态的内部过程，显示恢复进度和目标帧，但不宣称完整 replay 已验证。
   - `Replay Validation`：从已冻结记录和 bootstrap 独立重建、逐帧比较的验证会话。
   - 页面标题、状态色和可用命令随模式变化，不能只靠一行顶栏提示。

6. **为短记录和空记录提供正确视口**
   - 只有三帧时自动放大 0～最小可读窗口，并明确显示“记录仅包含 Frame 0…3”。
   - 没有 replay 记录时显示记录选择/捕获入口，不显示带未来 marker 的空五轨。
   - marker 使用 Replay 自身 validated TimelineRecord；禁止沿用 live 页面对象池中的残留节点。

7. **恢复编辑与诊断上下文**
   - 从 Behavior Card 或 RuntimeFrame 进入 Replay 时保存来源工作区、选中卡/节点、视口和 frame。
   - 返回时恢复来源上下文；Replay 验证不改变 Draft、Installed Deck、Published revision 或 live selected frame，除非用户显式选择同步查看。

#### 本页验收标准

- Replay 页面始终显示记录来源、frame range、bootstrap/catalog/session authority 身份和验证状态。
- 篡改 bootstrap JSON、catalog、固定 revision、roster 或任一帧 participant hash 都会产生结构化失败并定位首个分歧帧。
- `Passed`只能来自完整恢复和逐帧比较，普通 live 历史浏览或 Warm Replay 不会显示验证通过。
- RuntimeFrame 与 Replay 复用同一五轨组件，但命令和状态职责明确不同。
- Replay 模式不会通过“推进”或“从此重算”隐式修改 live future。
- 短记录不会铺满到帧上限，也不会显示 latest 之后的 marker。
- 退出 Replay 后原行为卡选择、逻辑时间轴视口和 RuntimeFrame 选中状态完整恢复。

### 14 — 从 Replay 返回行为卡的上下文恢复

![从 Replay 返回行为卡后的真实 Game 帧](../Images/CharacterTest/runtime-ai-lab-flow-audit-12-return-behavior-card-from-replay-2026-07-19.png)

#### 操作结果与结论

- 点击 `行为卡`后恢复到诊断前的行为卡工作区，顶部明确提示“已退回行为卡”。
- 右侧仍选中 `dash`阶段，四个 Stage 的时间轴视口与进入诊断前一致。
- selected/latest 仍为 Frame `3`，运行覆盖线与底部实际状态也得到保留。
- Preview Camera 正常恢复，Agent、目标、红色目标线和范围圆均可见；没有复现 F9 重开时的黑屏。
- 页面标题和运行动作仍为“等待/保持 / Wait or hold”，而时间轴仍是突进/攻击序列；既有身份错误没有因上下文恢复得到纠正。

普通工作标签切换的上下文保留基本通过：选择、视口、帧和 Preview 都没有被销毁或重置。这进一步缩小了黑屏问题范围——Preview Host 在 Behavior Card 与 Diagnostics 的挂载/卸载路径可恢复，而 F9 隐藏整个 Shell 后的重开路径不完整。

本步不应因为“恢复了错误身份”而判定整体通过。正确合同是既恢复交互上下文，也重新验证并显示同一行为卡身份链；恢复旧的错标题只能证明状态被保留，不能证明状态正确。

#### 问题与整改

| 优先级 | 问题 | 整改 |
| --- | --- | --- |
| P0 | 恢复后的行为卡身份仍是“等待/保持”与突进逻辑矛盾 | 返回时根据当前 Draft/source/candidate 重新校验身份链；不复用 runtime action 覆盖卡标题 |
| P1 | 顶部只提示“已退回行为卡”，未说明恢复了哪张卡、哪个 Draft 和 Frame | 使用 `已恢复：突进连击 · Draft · Frame 3`，并在身份失效时显示降级原因 |
| P1 | 诊断页来源与返回栈不可见 | Shell 保存明确的 return context，而不是只把工作标签切回 Behavior Card |
| P2 | 已正确恢复的节点/视口没有可验证的短时反馈 | 恢复时短暂高亮原选中 Stage/Transition，并保持滚动位置不跳动 |

#### 本页验收标准

- Behavior Card → Facts → RuntimeFrame → Replay → Behavior Card 后，卡、Draft、节点、视口、selected frame 和 Preview 全部恢复。
- 返回时重新验证卡身份；错误或已失效的 Draft/candidate 不会以旧缓存标题继续显示。
- F9 重开与普通标签返回使用同一幂等 Preview 挂载逻辑，均不会黑屏。
- 返回提示包含实际恢复的卡与帧，而不是只有泛化页面名称。

### 15 — 行为卡页生成历史与单帧回看

![播放约两秒并暂停后的真实 Game 帧](../Images/CharacterTest/runtime-ai-lab-flow-audit-13-after-live-play-pause-2026-07-19.png)

#### A. 生成可回看历史

- 初始 selected/latest 为 Frame 3，但仅捕获 1 帧，因此 `-1`正确禁用；页面没有 tooltip 或就近说明禁用原因。
- 点击播放、运行约两秒并再次暂停后，selected/latest 到达 Frame `120`，捕获量增加为 `118 / 900`，`-1`、`-10`进入可用状态。
- Preview 中 Agent/目标位置发生变化，帧轨道填充同步增长，说明播放、捕获与暂停主链路存在。
- 页面明确显示“暂停状态”，这一点比开始测试后只显示“测试已开”更易理解。
- 运行语义矛盾进一步加重：中央状态仍显示主动作 `Wait or hold`，页面标题仍是“等待/保持”，但行为时间轴底部显示 `Dash Strike 已运行 0.5s / 28f`。

#### 阶段性结论

RuntimeFrame 捕获和基本播放/暂停可用，`-1`最初禁用不是命令故障，而是缺少上一保留帧。但禁用原因完全依赖用户自己从远端 `已捕获 1/900`推断；正式控件应在本地显示“无更早保留帧”。

更重要的是，运行覆盖层与中央 runtime 状态似乎来自不同投影或不同对象。若 `Dash Strike 0.5s/28f`是逻辑时间轴的计划/预览进度，而当前权威主动作是 `Wait or hold`，必须明确标为“设计预览”而不是“实际”；若它声称是实际耗时，则与主动作状态冲突，必须产生诊断而非同时展示。

#### 本阶段整改要求

- 所有禁用的帧控制提供就近原因：无更早保留帧、已在最新帧、Warm Replay 中、会话锁定或恢复失败。
- selected/latest/captured/oldest retained 使用同一个紧凑状态组，不把推断信息拆散到顶栏和控制条两端。
- `计划预览`、`最近一次实际耗时`、`当前权威执行进度`使用不同名称和视觉，不允许都用无标签水平线表示。
- 权威当前主动作与“实际运行”覆盖不一致时显示结构化错误，并禁止将该次测试用于发布验证。
- 下一步使用 `-1`定位 Frame 119，核对 Preview 姿态、状态摘要和行为卡覆盖是否同步恢复。

#### B. `-1`单帧历史回看结果

![从 Frame 120 后退到 Frame 119 的真实 Game 帧](../Images/CharacterTest/runtime-ai-lab-flow-audit-14-history-frame-minus-one-2026-07-19.png)

- 点击 `-1`后 selected 从 Frame `120`正确变为 `119`，latest 保持 `120`，捕获量保持 `118 / 900`；已有未来没有被截断。
- 顶栏明确切换为“回看”，控制条显示 `选中 119 / 最新 120 / 上限 902`，并提示历史只读、建立新未来需要显式使用“从此重算”。

- 时间轴底部的 `Dash Strike`实际计数从 Frame 120 时的 `28f`回退到 `27f`，白色覆盖线也相应缩短，证明这部分覆盖投影响应了历史帧。
- Preview 的角色位置和姿态肉眼几乎不变；由于权威主动作仍为 `Wait or hold`，本次无法从动作变化证明离散姿态恢复，只能确认相机与实体仍正常显示。

#### 本页最终结论

单帧 seek、只读历史边界、selected/latest 分离和一部分运行覆盖同步通过；页面没有隐式删除未来，这符合安全合同。但行为卡核心逻辑状态没有直接投影到卡片，且 runtime action 与 Dash Strike 覆盖继续矛盾，因此只能判定“部分通过”。

补充整改要求：

- 历史帧必须直接恢复并显示当前 Stage、主动作生命周期、Detector Armed/Active/Hit、Pending Transition 和实际路径。
- Preview 旁显示 `历史回看 · Frame 119`，并在无姿态差异时仍能通过权威状态证明恢复完成。
- `从此重算`只在 selected < latest 时出现，点击后必须显示将失效的未来范围并二次确认。
- `最新`返回 live edge 后清除历史回看状态，但不得重启 session 或丢失行为卡选择/视口。

### 16 — 从历史帧返回最新帧

![从历史回看返回最新帧后的真实 Game 帧](../Images/CharacterTest/runtime-ai-lab-flow-audit-15-return-latest-frame-2026-07-19.png)

#### 操作结果与结论

- 点击 `最新`后 selected 从 Frame `119`恢复到 `120`，与 latest 再次一致；捕获量仍为 `118 / 900`。
- 顶栏从“回看”恢复为“暂停”，并提示已选择最新帧；没有隐式恢复实时播放。
- 历史状态下可用的“从此重算”重新变为禁用，说明破坏性分支入口至少遵守 `selected < latest`的显示边界。
- Preview 恢复到此前 Frame 120 的构图，`dash`选择、行为时间轴视口和实际计数 `28f`均保留。
- session 没有重启，latest 没有增长，已有历史也没有被删除。

该链路通过。它证明当前 selected/latest 状态机的最小安全闭环可用：历史后退不会截断未来，返回 latest 不会自动播放或重启。但返回后依然恢复了错误的“等待/保持”身份和缺乏卡片高亮的运行覆盖，因此通过范围仅限帧导航，不代表行为卡运行表现合格。

#### 本页验收标准

- `最新`只改变 selected frame，不隐式修改 latest、历史记录、session 或播放状态。
- 从历史回看返回后，Preview、Facts、Behavior Card runtime overlay 和 authority hash 同步指向 latest。
- “从此重算”在 latest 禁用；任何残留分支警告或历史标记被正确清除。
- 卡、Draft、节点选择和时间轴视口保持不变。

## 6. 总体结论与整改实施顺序

### 6.1 总体结论

本轮在真实 Play Mode、当前 Game View 分辨率下按玩家可达路径走查，最终结论为 **Changes requested**。底层安装/移除数据同步、COW Draft 隔离、普通工作标签上下文恢复、RuntimeFrame 播放/暂停、只读历史后退和返回 latest 已表现出可复用基础；但当前 UI 仍不能作为正式玩家玩法与 Runtime AI Lab 的统一工作台验收。

阻断验收的四组 P0 是：

1. **身份与权威状态不可信**：从“突进连击”进入后，页面和 runtime 长期显示“等待/保持 / Wait or hold”，时间轴和实际覆盖却显示 Dash Strike；用户无法证明正在编辑、测试或发布哪张卡。
2. **Shell 与页面导航不成立**：Setup 在正常路径不可达，F9 重开恢复错误工作区并出现 Preview 黑帧；Player Deck 是否为覆盖层及 Preview 的具体生命周期根因仍待源码验证。
3. **诊断时间数据不可信**：latest 仅为 3 时，RuntimeFrame/Replay 在未来区显示无来源 marker；捕获、未模拟、淘汰区没有权威边界。
4. **Replay 只有名称没有验证证据**：缺少记录来源、bootstrap/catalog/session authority 恢复与逐帧 hash 结果，无法证明回放验证实际发生。

此外，推荐预设会静默移除玩家刚安装的卡且不可撤销，属于玩家装配层的 P0 交互风险。

### 6.2 整改 Epic 与强制预拆方向

以下 A–G 是 `Remediation Epic`，只用于根因归组和依赖排序；它们不是固定流程中的 `Candidate`，不得直接进入 `Design In Progress`或授权编码。只有按本节预拆方向形成单一根因、单一权威边界且可独立验收的子切片，写入独立 `Docs/Tasks/`设计并通过 `Design Review → Design Accepted`后，才可实现。

本轮走查文档本身也必须先完成独立文档评审并提交；在此之前不得把 A1 或其他子切片标记为 `Design In Progress`。

#### Epic A — 身份与投影合同（Remediation Epic）

- 冻结 `Player Card → Published revision → COW Draft → Session Candidate → Runtime Card/Stage/Action`身份链。
- ViewModel 分开“当前编辑对象”“当前运行对象”“本帧已提交状态”“下一候选”，禁止用 runtime action 覆盖卡标题。
- RuntimeFrame marker 严格从 typed record 构建并校验范围，对象池清理残留。
- 为上述 P0 增加 focused C# 投影测试；本切片通过前不开始正式 FairyGUI 重排。

评审门禁：同一帧不再出现无解释的“等待/保持、Dash Strike、Wait or hold”并列；latest 之后无 marker。

#### Epic B — 单一 Shell 与正式工作区（Remediation Epic）

- 正式 `ActiveWorkspace`至少包含 PlayerDeck、Setup、BehaviorCard、Facts、RuntimeFrame、Replay。
- F9 只显隐 Shell 并保存用户最后可见工作区；页面返回使用明确导航命令。
- Player Deck 增加 `确认卡组并进入实验设置`，使 Setup 可达；Setup 提供返回卡组与开始实验。
- 每次只挂载一个全尺寸不透明工作区；统一 Preview Host 幂等挂载和错误占位。

评审门禁：从 Play 到装配、Setup、测试、诊断、返回和 F9 重开均有可预测路径，无遮挡、穿透和黑帧。

#### Epic C — 玩家牌库与装配体验（Remediation Epic）

- 牌库卡和 Installed Deck 使用统一卡面组件，完成本地安装/移除反馈、槽位/费用变化和低战力诊断。
- 推荐预设先显示新增/保留/移除/费用差异，再显式确认，并提供一次撤销。
- Draft、Unavailable/Incompatible、已安装、不可重复和费用不足在卡面就近表达。

评审门禁：单点操作无需猜测结果；任何覆盖玩家选择的操作均可预览、确认和撤销。

#### Epic D — 按权威效果图重建 Behavior Card（Remediation Epic）

- 下半区以大 Stage 卡为唯一主要编辑载体；卡内显示动作、Detector、Transition、时间和运行状态。
- 移除常驻节点库、固定 Inspector、重复主动作轨和独立运行覆盖轨；添加操作改为可收起面板。

评审门禁：无需读取左侧说明或右侧 Inspector，即可从 Stage 卡读懂并编辑完整逻辑；运行状态直接覆盖卡片。

#### Epic E — 历史帧上的完整行为逻辑恢复（Remediation Epic）
