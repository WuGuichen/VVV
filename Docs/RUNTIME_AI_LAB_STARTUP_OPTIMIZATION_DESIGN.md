# Runtime AI Lab 启动优化设计

> Status: Design
>
> 日期：2026-09-13。实施状态：方案整理完成，分配策略与二进制迁移尚未实施；当前只有诊断标记和已有的静止 UI 优化。
>
> 依据：[启动分配问题反馈](RUNTIME_AI_LAB_STARTUP_ISSUE_REPORT.md)。本文为建议设计，不覆盖现有 Runtime、Network、身份目录及制作事务合同。

## 1. 决策摘要

推荐顺序是：**先修历史存储和恢复策略、整合内容准备与 ID 事务，再交付制作期编译的二进制运行产物；最后根据剩余数据处理 UI、Spawn 和启动调度。**

从影响判断，调用组织和生命周期优先级更高。诊断存储约 484.3 MiB 不经过 JSON；动作加载和 ID 查询的成本则是“重复次数 × 每次准备成本”。二进制可以降低后一项，不能自动减少前一项。

从执行顺序判断，可先交付职责边界明确的 ID 批处理切片，同时推进诊断存储和动作内容准备。不要为了等待二进制系统，推迟前三个已证实问题的修复。本文不提供未经实施验证的工期估算。

目标不是把一次 5 秒阻塞平均分散到多个画面帧。首先减少无效工作和分配，再处理确有必要的初始化工作如何保持响应。

## 2. 边界与现有合同

- 保留逻辑模拟 Tick、Bootstrap 注册、首个可见 authority 状态及必要历史记录频率。
- 保留 Server/Client 双世界的执行隔离、恢复失败保护、Seek、分支 pin、历史来源定位和回放一致性。
- 字段 Key、Schema ID、Contributor ID 和定义 ID 继续使用现有数值协议；Runtime 不按显示名称推断身份，不现场分配定义 ID。
- 已有配置内容哈希语义、空值语义、浮点量化、遍历顺序和整数目录规则不能因格式优化而改变。
- 固定 16 字节会话组合仍是 XXH64 / AlgorithmId 2 / Schema 1001 / Layout 1；状态编码仍遵循现有 v3 合同。本设计不重选帧哈希算法。
- 当前 CharacterTest 快照 38、回放 7。仅新增内容产物格式不自动触发网络/回放升版；实际改变 payload、状态语义或兼容性合同的切片必须同步评审并升版。
- Runtime 不依赖 UnityEditor；noEngine 不引入 UnityEngine。正式 Unity 资产通过 Editor 或仓库生成器生成，保留 .meta。
- 当前已有 UI/身份迁移改动和用户草稿不回退；本方案不是全仓字符串或所有 JSON 的治理计划。

权威入口：[Runtime](Interfaces/Runtime.md)、[Network](Interfaces/Network.md)、[API 标准](API_STANDARDS.md)、[质量门禁](QUALITY_GATE.md)、[帧同步开发指南](Guides/CHARACTER_TEST_FRAME_SYNC_DEVELOPMENT.md)。

## 3. 目标数据流

~~~mermaid
flowchart LR
    A[制作源：动作与目录 JSON] --> B[制作事务：校验 / 分配 ID / revision 与 hash]
    B --> C[准备不可变内容快照]
    C --> D[生成带版本和指纹的二进制产物]
    D --> E[加载并验证一次]
    E --> F[不可变动作定义与整数索引]
    F --> G[Server 独立执行态]
    F --> H[Client 独立执行态]
    F --> I[会话权威与卡组只读查询]
    G --> J[按有效历史存储诊断数据]
    H --> J
    J --> K[稳定句柄 / 恢复快照 / 分支 pin]
~~~

内容准备属于制作、导入、显式保存或会话准备边界。正常 Tick 只读已经准备好的数值索引和定义；启动无需反复重建同一内容图。共享定义的前提是已经证明其深层不可变，不是仅给字段加 readonly。

## 4. 切片 A：整数目录的一次事务批处理

对应 STARTUP-003。建议作为首个独立交付切片。

### 4.1 目标接口和所有者

制作层提供批量解析/分配入口，输入为去重的 (domainId, stableSourceKey) 请求，输出为本次目录 revision/hash 和全部整数结果。具体 API 名称在实现时进入所属 Editor/制作接口；不能把该入口暴露为 Runtime 取号 API。

流程：

1. 从 workspace 收集所需身份，按稳定的制作身份去重。同一 card 被多个 group 引用时，definition ID 只解析一次。
2. 进入一次排他事务，读取目录并校验 schema、hash、重复项、active/retired 和 nextId。
3. 在同一内存快照中完成全部查询；已有 ID 保持原值，只有真正新增的内容分配正整数。
4. 全部请求通过后生成结果。确有新号时才更新一次 revision/hash 并提交一次目录文件；全为已有 ID 时不写目录。
5. 在结果完整、验证成功后批量更新 workspace 的数值字段，进入既有草稿保存事务。

顺序或排序不得重编号已有内容；新增内容的分配结果必须正式保存。显示名称的改变不构成新身份。

### 4.2 失败与并发

目录文件和 workspace 文件是两个提交对象，不能靠两次 File.Replace 宣称跨文件原子性。优先采用“持久化 ID 预留先成功、workspace 再引用”的幂等方案：后续 workspace 保存失败时，已预留 ID 保持已占用；重试按稳定 sourceKey 取回同一 ID，不回收、不复用。若确需整体回滚，应使用现有事务日志/恢复机制明确实现，不能部分更新内存对象后静默继续。

目录变化必须通过现有 expected revision/hash 或排他事务规则检测。缓存只能复用已验证版本；不能用文件路径相同或仅时间戳相同证明内容未变。

### 4.3 验收

- 同一显式保存事务中的全目录解析/结构校验不随 entry 数量重复：冷事务最多各一次，已持有合法快照的路径复用该版本。提交前必要的文件 hash 并发检测单列为常数次 I/O；请求收集、逐项查询和 workspace 序列化仍按内容规模计量。
- 全部 ID 已存在时无目录写入、revision 不变；新增/复制、retired、缺失和冲突行为正确。
- 重复保存、相同请求顺序变化、跨 group 重复引用不改变已分配 ID。
- 覆盖写 staging 失败、替换失败、并发更改、进程中断后的重试；workspace 不出现半批数值更新。
- workspace 保存失败要明确返回失败，持久化但尚未引用的 ID 预留可审计；重试必须取回同一 sourceKey 的同一 ID。目录与 workspace 的 revision 分属各自事务，不能假定数值相同，也不能把部分完成报告为整体成功。
- 单次已有 ID 查询不再触发整目录 JSON Parse / DeepClone / CanonicalHash；批量整体分配仍据实计量，不把事务准备成本藏到另一帧。

## 5. 切片 B：历史诊断存储与恢复快照

对应 STARTUP-001，按分配影响优先级最高。

### 5.1 推荐设计

将“可保留的帧上限”与“已经物化的诊断存储量”分离。空槽只保存轻量状态，Facts/Candidates 载荷按实际需要的 Agent 和记录量持有；不会因为帧上限为 900，就立即创建 7,232 组最大容量数组。

先独立修复恢复复制：恢复 Clone 只复制被有效句柄或 pin 引用的载荷，保留槽位/generation 元数据和映射，禁止先完整构造全容量 arena 再覆盖。随后再引入分块存储与受控容量准备。

恢复快照可保留不可变块引用或复制有效载荷；两者均需显式所有权。已封存块在被历史、选中帧、恢复目标、分支事务引用期间不能覆盖。新增写入落到独立可写空间，发布后转为不可变。保留稳定句柄到存储块的映射，重用槽位时更新 generation，过期句柄必须拒绝。

“只复制有效数据”不能等同于只复制当前时间线显示的记录。必须覆盖 pending/staging、被 pin 的 branch future、待恢复快照仍引用的数据，并保留 free list、generation 和 overflow 语义。它是诊断存储生命周期调整，不应扩展成无关资产目录的回收系统。

### 5.2 保持稳态无分配的办法

先按明确的 Agent/记录预算准备少量块；在会话准备或显式扩容边界补足可写容量。正式 Capture 不悄悄分配、不丢必要记录。达到边界时按照现有 overflow/容量合同处理，或在推进前完成可观测的扩容准备。

块大小和预热量由实际 trace 密度、retained frames、恢复并发数实测决定，不在本文凭空冻结一个容量。预热分配、峰值存活内存、稳态 Capture 和恢复复制必须一起计量。

### 5.3 验收

- 无有效历史的恢复快照不分配全容量 Facts/Candidates。
- 相同有效历史、不同保留帧上限下，恢复载荷分配随有效载荷规模变化，而不是随最大容量成倍增长；轻量索引开销单列。
- 历史帧只读；分支、裁剪、恢复成功/失败、pin/unpin、陈旧句柄及 overflow 的行为与原合同一致。
- 对照旧存储与新存储，相同内容/命令下的 authority hash、FrameBuffer 选择、Count/SelectedIndex/RetainedStartFrame、逻辑 trace identity 和 ReplayValidation 结果一致。诊断载荷本身不进入 authority/replay hash，仍需验证存储改动没有扰动模拟推进或历史读取；内部物理块索引不得替代稳定身份。
- 900 / 1,800 帧以及不同 Agent 数的满容量测试；持续采集、Seek、分支未来和恢复快照同时持有时均正确。
- 稳态 Capture 无新增临时分配；分配计数器必须有正向对照。内存上限明确，不能把全量预分配改成无界增长。

## 6. 切片 C：动作内容一次准备，执行态独立

对应 STARTUP-002。

### 6.1 所有者与接口分离

拆开当前 Load 的两项责任：

- 准备内容：源读取/合并、调参应用、导入、结构校验、定义索引和语义指纹。
- 创建执行实例：当前帧、动作进度、目标、事件缓冲、实体绑定、动作执行状态和回放状态。

由会话准备上下文持有一个经过验证的不可变内容快照，显式传给 Server/Client、SessionAuthority 和 PlayerDeck。TryCreateCatalog / ProjectCatalogLoader 接收现有只读 references，避免嵌套调用再次隐式 Load。

先审计定义对象内部数组、集合、setter 和调用方的写入；冻结后才共享。禁止把整个 CharacterActionRuntime 做成静态单例，禁止缓存实体、场景组件或可变 pose/equipment 绑定。依赖真实角色几何、装备、动作选择和权威姿态的 tactical inputs 仍按其自身依赖重新准备。

### 6.2 缓存失效

准备快照绑定全部有效输入：动作/动作集、reaction/landing profile、调参内容、导入器/验证规则版本和相关整数目录指纹。来源变更、显式重载或制作事务完成时建立新版本；同一会话内重复请求复用旧版本。

已有运行会话持有其冻结版本；新会话获取新版本。是否允许运行会话热切换，继续走现有显式热重载/兼容性流程，不能由缓存自动替换。持有者释放后回收旧版本，避免跨 Domain Reload 或会话重启累积。

### 6.3 验收

- 同一输入指纹、同一次会话准备，昂贵的动作内容准备最多一次；六个消费入口不再各读源 JSON。
- Server/Client 状态、命令和事件完全独立；修改一个世界的执行状态不影响另一个。
- 源文件、调参、目录映射和生成器版本变化能够失效；相同内容不同加载顺序具有相同内容身份。
- 回放、恢复、历史 frozen source 与 event/source map 保留其原始内容快照，缺失或不匹配明确失败。

## 7. 二进制是否能根治，以及应该怎样采用

### 7.1 能力边界

| 当前问题 | 仅更换序列化格式 | 配套正确结构后 |
| --- | --- | --- |
| 484.3 MiB 诊断存储 Clone / 预分配 | 无直接作用 | 有效载荷存储、稳定句柄和恢复所有权解决 |
| 动作配置加载 6 次 | 每次可能更便宜，重复次数仍是 6 | 一次内容准备 + 二进制读取共同改善 |
| 已有 ID 查询重复整目录事务 | 扫描/重建可能更便宜，事务仍重复 | 批处理、版本快照与数值索引解决重复工作 |
| JObject / JArray / 字符串图 | 有机会显著降低 | 制作期编译为紧凑数值数据，运行时直接读取 |
| UI 整树重建与角色 GameObject 创建 | 无直接作用 | 分别调整 UI 生命周期和 Spawn 实现 |
| 首次 JIT | 不保证改善 | 需单独确认调用面与预热，不能承诺换格式消除 |

**建议将 JSON 保留为可审查的制作源，将运行时交付形态改为经过编译的数值二进制产物。** JSON 是否作为作者文件格式，与运行时是否解析 JSON，是两个独立决策。没有必要为了运行时性能同步改掉 Git diff、编辑、迁移所用的源格式。

把 JSON 文本压缩后再解析、把同一对象图换成通用二进制反序列化、加载二进制后再构造完整 JObject/DTO 图，都不能作为“根治完成”。若未来也要替换制作源格式，须另行解决可审查 diff、合并和迁移；它不能代替前三个切片。

### 7.2 候选与选型

| 方案 | 本项目用途 | 主要成本或限制 | 建议 |
| --- | --- | --- | --- |
| 现有 JSON + 一次加载的冻结类型快照 | 不换格式先关闭重复加载 | 首次解析成本仍存在 | 作为切片 C 的基线及可独立交付收益 |
| 自定义/生成式数值二进制表 | 动作定义、整数目录、数值索引等固定领域数据 | 自行维护 schema、验证、生成器和调试工具 | 优先做窄原型；未实测前不冻结为赢家 |
| FlatBuffers C# | 在持有的缓冲区上读取 schema 化表、排序数值索引 | 生成代码、缓冲区生命周期、访问器开销、字符串读取行为需要验证 | 作为读取型候选，必须验证当前 Unity 安全 C# 边界 |
| MessagePack 的显式整数 schema | 成熟通用值编码，便于替换部分配置传输 | 格式本身不保证无对象图重建或无反射 | 作为对照；不凭格式名称宣称最快 |

FlatBuffers 官方 C# 文档说明可用排序向量按 key 查找而不先解包成 Dictionary；这支持其作为直接读取候选，但不等于任何调用方式都零分配。[官方 C# 文档](https://flatbuffers.dev/languages/c_sharp/)。MessagePack 定义了二进制值编码，其规范不能证明某个 C# 序列化器在本项目最快或不分配对象。[官方格式规范](https://github.com/msgpack/msgpack/blob/master/spec.md)。

本项目目前没有上述二进制候选的等价性能结果，因此不采用第三方宣传倍率，不新增运行时包，不更换 Mono/IL2CPP/Burst 后端，也不放宽 allowUnsafeCode/noEngine 边界。需要依赖的候选应先证明当前目标环境和包边界可用。

### 7.3 建议的运行产物内容

以下为待实现的格式要求，不是已冻结的新公共协议编号：

| 部分 | 要求 |
| --- | --- |
| 头部 | Magic、独立格式版本、字节序/长度、段表、生成器版本或标识 |
| 内容身份 | 现有语义/内容指纹、源 schema、相关目录 revision/hash、依赖指纹 |
| 数值定义 | 显式 ID、枚举、固定宽度字段、数量和偏移；不按声明顺序重编号 |
| 只读索引 | domain/definition ID 到数据位置；重复、缺失和 retired 引用在加载时验证 |
| 动作/程序数据 | 必要的定义、条件、事件、量化值、映射；保持现有顺序与语义 |
| 历史定位信息 | program identity、稳定 event/source 映射与 frozen source 所需内容，允许独立诊断段 |
| 文本与摘要 | 显示文本可以独立加载；真正文本内容保持 null/空值及字符语义，摘要保留完整位宽 |
| 完整性 | 产物字节校验和段边界检查；artifact checksum 与游戏语义指纹分开 |

安全 C# 中优先使用固定宽度读取与预先验证的偏移/长度，不把托管对象布局或结构体 padding 当作文件协议。加载先检查版本、长度、数量、溢出和数值引用，再发布准备快照；失败时不能部分修改世界。

字符串表只用于确需保留的文字。字段 Key 和内容身份不能因为存在字符串表而退回名称查找。产物也不能为省空间丢弃原来参与内容一致性或历史定位的字段。如果重排 event/stage/detector 数据，必须保留稳定 source map；二进制数组下标不能替代现有 event/source 身份。

### 7.4 生成、提交与失效

制作流程为：稳定读取源快照 → 完成目录事务 → 校验全部依赖 → 生成候选产物 → 校验产物 → 通过 manifest/现有生成器事务发布。

正式产物由所属制作生成器/Editor 生成；Unity 资产连同 .meta 纳入版本管理。机器缓存仍留在 Library 等本地目录。不要建立两份可分别编辑的 JSON/二进制事实源；二进制必须能从指定源与工具版本重建。

Editor 发现产物过期时，在明确的准备边界重新生成；正式 Player/会话准备遇到不兼容或缺失产物时，在修改世界前拒绝并提供明确错误。Player 的预期内容指纹来自发布 manifest 和现有内容/会话合同，不应为了验证二进制而重新读取全部源 JSON。Editor 的源变更检测在导入/制作边界准备指纹。不能在 Tick 中偷偷退回 JSON 导入、补 ID 或重新编译。迁移期间的旧入口只用于独立验证，不在线双算状态哈希。

二进制 artifact 的排列/压缩变化可能改变文件 checksum，但在内容语义相同时不应无故改变既有动作 ID、内容语义 hash 或帧结果。继续使用现有内容/会话一致性机制表达真正的依赖变化；格式版本与回放/网络版本分开管理，实际语义改变时才同步调整兼容性协议。

## 8. 实施顺序与可评审交付物

| 阶段 | 交付物 | 关闭条件 |
| --- | --- | --- |
| S0 基线冻结 | 内容/命令 manifest、Profiler 设置、冷启动/重复测试证据、计数器可用性 | 同场景可重复；父子开销不重复统计 |
| S1 ID 事务 | 批量目录 API、显式保存接入、失败重试测试 | STARTUP-003 的整目录查询放大关闭 |
| S2 历史存储 | 有效载荷恢复、分块/容量策略、句柄与 pin 回归 | STARTUP-001 的全容量载荷复制关闭，历史合同通过 |
| S3 内容准备 | 冻结定义快照、显式注入、独立执行态、失效测试 | 同一内容昂贵准备一次，6 次重复源加载关闭 |
| S4 二进制切片 | 动作/目录原型、生成器、独立 decoder、格式测试和选型报告 | 等价正确性与 Mono Editor/Player 实测均满足目标，正式入口切换 |
| S5 剩余启动工作 | 残余采样；按证据处理 UI shell 重建、Spawn 或阶段调度 | 分别证明局部和整次启动收益，不隐藏成本 |

S1 可先交付；S2/S3 在明确文件所有权后可并行。S4 的 schema 原型可以提前探索，但最终加载入口应建立在 S3 的所有者边界上，避免换完格式仍有六次加载。每个切片保持可编译，最后同步实际改变的接口、制作和兼容性文档。

## 9. 性能与正确性验收

### 9.1 测量组合

固定 Windows x64 / Unity 6000.5 / Mono Editor 和 Mono Player，关闭 Deep Profiling。记录进程是否首次加载、源内容指纹、帧上限、Agent 数、卡片/事件数量、命令序列、采集开关和缓存状态。

- Editor 首次会话：新 Editor/Domain 的内容与 JIT 冷状态；单列进程内首次成本，不宣称操作系统文件缓存也已冷却。
- 重复测试：相同内容在已有 Editor 中重新开始；不能用它代替首次启动指标。
- 改动后启动：动作、调参、整数目录或卡内容改变，确认失效与重建成本。
- 恢复/历史：有效历史 0 / 少量 / 接近上限；900 / 1,800 帧和不同 Agent 数。
- Player：正常加载、错误产物、重复建会话；不包含 Editor 制作事务。

二进制候选使用正式编译的入口，在预热后轮换执行至少 31 个批次；测整个加载/验证/建立索引的过程及后续读取，不能只比较反序列化函数。单独记录文件读取、解码/解压、验证、对象物化、索引准备及保留内存。压缩候选把解压成本算入冷启动。

启动端到端分别做可重复的冷/热样本，报告样本量、均值、中位数、P95、总分配、分配次数、峰值/保留内存及首个可操作画面的延迟。样本不足时保留原始分布，不把少数样本的 P95 当稳定结论。

### 9.2 完成标准

- 三个主要问题的结构验收通过：不再克隆未用的全容量诊断载荷、同内容准备一次、同目录事务批量解析一次。
- 主要目标阶段的总分配和 CPU 均低于对应基线；整次启动不能持续回退。不得将当前 81.9% 的归因比例直接写成可实现节省比例。
- 二进制候选只有在正确性通过且目标环境整次准备耗时/分配优于 S3 的 JSON 一次加载基线时，才成为正式生产赢家。没有显著收益就不承担格式迁移成本；选择结果记录全部样本。
- 预热后的正常 Capture/Tick 不新增临时分配；计数器正向对照通过。不要求整个启动零分配，也不接受只凭 0 GC 宣布性能成功。
- 双世界相同命令序列的状态转换、战斗结果和既有 hash 合同不变；历史、Seek、恢复失败、分支隔离、固定摘要、ID 迁移和内容失效专项通过。
- 损坏/过期/错误版本、重复/缺失/退休 ID、非法偏移和未知必需段在世界修改前拒绝；二进制 golden、源语义对照、不同加载顺序和重复生成测试通过。
- Unity 使用 validate_unity_scripts 验证 refresh、compile、domain reload、Editor ready、Console 零错误。涉及包 API 时补命中包边界/Local Consumer 检查。既有不相关失败独立记录，不能删测试掩盖。

## 10. 不应采用的捷径

- 只调大 UI 刷新间隔，或减少必要模拟/历史采集频率。
- 只改 JSON 文件扩展名、压缩 JSON，或把对象图换一种 serializer 后宣布根治。
- 只缓存路径、显示名称或时间戳，忽略依赖和内容版本。
- 把服务器/客户端可变执行对象合并，或让历史快照指向正在复用的数组。
- 取消 retired、revision/hash 校验来缩短目录查询，或在启动/正常 Tick 现场分配定义 ID。
- 用异步分帧隐藏总分配，或将预热/摘要准备移动到其它阶段后排除计量。
- 将一次局部微基准的倍率写成整帧/整次启动的倍率。
